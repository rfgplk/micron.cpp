Changes
  binary64 generation uses packed integer powers and base-10^9 limbs instead
  of repeated decimal digit shifts. The read-only tables occupy about 16 KiB.
  Rendering uses bounded SIMD digit blocks and avoids redundant buffer passes.
  Bounded char parsing scans 16-byte prefixes and eight-digit groups, with
  scalar tails and preserved unbounded, wide-character and constexpr paths.
  Canonical scalar IO uses unaligned-safe fixed-size copies; header validation
  compares eight bytes at once. Wire bytes and constexpr behavior are unchanged.
  Deserialization reuses string, flat vector and nested element capacities.
  Symbolic output starts with local scratch and allocates overflow lazily;
  a caller-scratch overload and local arbint conversion work remove normal
  repeated-writer allocations. Sink spans must be consumed synchronously.

  Scalar IO: one operation writes/reads 256 u64 values. Vector and string
  payloads: 4 KiB. Nested payload: 16 strings of 64 bytes. Symbolic case:
  a small expression with a symbol, integer coefficient and integer power.
  The original caller-scratch case falls back to the original default API.
  Allocation values above count the selected container allocator only.
  Symbolic zeroes do not measure its old direct VM reservations. A separate
  allocator-stats test verifies zero heap calls for normal caller-scratch IO.
  Byte framing is already a copy path; the data show no material change.
  Large symbolic gains come from removing an oversized per-call VM scratch
  reservation, and are specific to repeated generation of small expressions.

Measurement limits
  This is a shared host, without fixed frequency or an exclusive CPU. CPU
  time excludes descheduling; wall time and user PMU counters remain in JSON.
  Original-code calibration targets 150 ms; the same operation count is used
  for optimized code, so the fastest optimized cases run for much less time.
  Small differences are noise; these results describe the fixed workloads
  and establish neither universal speedups nor a global throughput maximum.

Backend coverage
  amd64/i386: SSE2 baseline; SSSE3 reductions when compile flags authorize it.
  arm32/aarch64: NEON validation, packed reduction, rendering and ASCII paths.
  wasm: SIMD128 and scalar fallback; compiled and executed under Node.
  MICRON_NO_SIMD and constexpr: scalar algorithms. No runtime CPU detection.
  Real object inspection confirms SSE2 floors and NEON/SIMD128 instructions.
  ARM benchmark runs use QEMU and prove correctness, not native performance.
  Wasm numeric/serialization benchmarks run; symbolic arenas still require
  virtual-memory reservation and are excluded on that backend.

Validation and independent review
  Initial 15 focused runtime cells passed, covering all targets, scalar/SIMD,
  sanitizers and existing decimal/canonical/symbolic/arbint/parse suites.
  After review: 12 focused runtime/codegen checks passed. Final canonical
  checks passed on native, i386, both ARM targets and wasm scalar/SIMD.
  Seven real codegen profiles and five cross-target benchmark smoke profiles
  passed. Cross-target benchmark checksums agree with native results.
  Tests cover all binary64 exponents, random mantissas, exact expansion
  against the original algorithm, misalignment, every SIMD byte lane, guard
  pages, output canaries, failed writes, truncated frames and capacity reuse.
  Three new independent gpt-6.1-sol agents at max effort reviewed memory
  correctness, UB, out-of-bounds access and corruption. Numeric review found
  no defects. Serialization review caught eager malformed-input allocation;
  symbolic review caught a missing arithmetic guard in the new overload.
  Both findings are fixed with regression tests and resolved follow-ups.
  No outstanding introduced memory-safety findings in the scoped reviews.
  Full repository compile matrices and unrelated suites were not run.

Alias follow-up
  The x86 decimal backend now uses the existing micron::simd::sse aliases
  through src/simd/aliases.hpp. All required aliases already existed. ARM
  decimal kernels contain vector expressions rather than raw NEON calls;
  wasm is unchanged. Complete compile-probe object files are byte-identical
  before/after for GCC and Clang, amd64 native/base and i386 base. Five
  runtime profiles pass: GCC native/base, i386 native/base and Clang base
  with ASan+UBSan. Detailed commands and hashes are in the validation JSON.
