usize

Defined in header <micron/types.hpp>.

Unsigned type of sizeof, used for object sizes and container indices. The aliases in this group follow the target pointer width.

Related types

TypeDefinition and use
size_t, usizedecltype(sizeof(0)); unsigned, 32 or 64 bits according to the target.
ptrdiff_tCompiler pointer-subtraction type, __PTRDIFF_TYPE__; signed.
intptr_t, ssize_t__INTPTR_TYPE__; signed pointer-width integer, checked to be the same type as ptrdiff_t on supported targets.
uintptr_tdecltype(sizeof(0)), rather than the potentially redefined __UINTPTR_TYPE__.
ptr_t, addr_tAliases of uintptr_t for numeric pointer and address values; neither owns storage.
p64Alias of uintptr_t, including on 32-bit targets; the name does not guarantee 64 bits.

Notes

Pointer-width aliases are suitable for native addresses and lengths. Use an explicitly sized integer for a stored field whose width must remain unchanged across targets.

Defined in header <micron/types.hpp>.

byte

Defined in header <micron/types.hpp>.

Alias of uint8_t, an unsigned character type with 8 bits. pnt_t is an additional alias of byte.

Notes

byte supports ordinary integer arithmetic and conversions. It is used for raw buffers and byte counts; it is not a scoped enumeration. A pnt_t value is a byte, despite the pointer-like spelling.

f16

Defined in header <micron/types.hpp>.

Compiler-dependent floating-point alias. The f16 and f128 names do not specify the same precision on every supported compiler and target.

Representation

ff always names float; df always names double; flong always names long double. The representation of long double follows the target ABI: it need not be the same as GCC amd64 _Float128. Serializing a native floating object therefore requires an explicit format choice.

micron::max_align_t

Defined in header <micron/types.hpp>.

Union whose alignment accommodates its members: the ordinary integer and floating-point types and void*.

Notes

The union includes char, short, int, long, long long, float, double, long double, and void*. Its alignment does not establish support for a user-defined over-aligned type. It carries no allocator or storage-ownership behavior.
