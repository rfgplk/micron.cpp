micron::chan_status

Defined in header <micron/tasks/async_channel.hpp>.

A nonblocking channel-receive status: ok, empty, or closed.

Receive result

chan_pull<T> contains bool ok and an owned T value. Awaited pulls return true with a moved received value, or false with T{} when closed and drained. chan_status::empty means no value was obtained from a still-open channel at that observation; concurrent producers/close can immediately change the state. These result types add no channel ownership or synchronization.

micron::async_channel

Defined in header <micron/tasks/async_channel.hpp>.

A bounded FIFO MPMC channel combining a Crossbeam ring with coroutine item/space semaphores.

Capacity and transfer

Cap defaults to 256 and should be positive. The ring rounds its allocation to a power-of-two capacity, while the space semaphore starts at exactly Cap, so channel admission uses Cap slots even when the ring has more physical slots. The ring allocation is owned by the channel; values are constructed/published and consumed according to that queue's type constraints. Pull paths also require T{}.

Awaited push(T) waits for space, rejects a closed channel, publishes the moved value, and posts an item. pull() waits for an item and returns chan_pull<T>. Bulk push copies a source span; bulk pull move-assigns a destination span and returns the transferred count. Those spans are borrowed until completion. Bulk counts are converted to signed 64-bit permit requests and must be representable.

post(T) and try_pull(out) do not deliberately suspend for missing space/items, but can spin on a reserved ring cell or while semaphore release waits for registration. They are not bounded-step lock-free calls. close() marks closed and aborts both semaphores, waking blocked operations; consumers can drain already buffered values. A producer that passed a close check can still race close and publish, so externally order final closure before treating closed-and-drained as permanent.

There is no reopening. Destroy only after all producers/consumers and suspended operations finish. Steady transfer uses constant queue/permit bookkeeping excluding contention and element costs; bulk work is linear in transferred values, and close can wake a linear number of waiters.

Lifetime and resumption

Suspended operations retain pointers to waiter nodes inside coroutine frames. The primitive, frame, and any referenced data must remain live at stable addresses until the operation completes. These primitives have no general cancellation registration or destructor that removes a queued waiter. Destroying a waiting task can therefore leave a dangling registration.

Wakeup submits a frame to the global engine when one exists, otherwise resumes it inline on the notifying thread. Callers must allow continuation execution and reentry around notification. Internal list locks spin briefly; suspending the coroutine does not eliminate all spinning from the implementation. No FIFO or starvation bound follows from an awaitable interface.
