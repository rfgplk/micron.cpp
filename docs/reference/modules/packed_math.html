Packed mathematical functions

From micron reference
micron reference › Numerics and mathematics

Lane-wise real mathematical functions over raw SIMD register types, with target-specific polynomial, table, CORDIC, hardware and scalar-lane implementations. A packed type's existence does not imply that every mathematical function has an overload for its width or enabled ISA.

Input types and selection

The native packed_real concept accepts f128, d128 where present, and enabled x86 f256/d256/f512/d512 register aliases. These are raw register types rather than v128/v256/v512 packet classes. elem_of/elem_t identify f32 or f64 coefficients and lanes_of/lanes_v identify the coefficient count. Native ARM composite 256-bit register records are not admitted by this packed-math concept. WebAssembly uses packet traits and accepts its real 128-bit values and 256/512-bit composites.

Functions return a new packed value without allocating or retaining input storage. Pointer-output sincos and atan2_bl_x4 variants require valid, sufficiently sized writable destinations; they do not allocate results or return status records. Availability and algorithm choice follow compile-time feature macros. The concrete packed overloads in these headers take no accuracy-policy argument; scalar policy types do not by themselves supply a missing native packed overload or a correct-rounding certificate.

Availability notes

math/simd.hpp includes dispatch, CORDIC, exp, log, manipulation, sqrt and trig headers, but not atrig.hpp. Include atrig.hpp for atan_bl, atan2_bl, atan2_pos, atan2_bl_x4 and have_atan2_packed. The generic packed_real classification is broader than each function's implemented overload set: accepting a register in that concept does not establish that log or trigonometric operations exist for it. Native x86 SSE-only builds do not acquire these AVX2-gated overloads merely because f128/d128 types are defined.

WebAssembly packed.hpp supplies sqrt/rsqrt, exp/exp2/exp10/expm1, log/log2/log10/log1p, sin/cos/tan, fabs/fneg/copysign, floor/ceil/trunc/rint and sincos by unpacking and applying scalar mkbits functions. Its sin_cordic/cos_cordic/tan_cordic/sincos_cordic names forward to ordinary trigonometric functions, rather than the native packed CORDIC loops. Composite width denotes storage and lane count, not a native 256/512-bit WebAssembly instruction.

Square root and reciprocal square root

sqrt uses hardware vector square root on x86 and ARM64. ARMv7 f32 uses reciprocal-square-root estimation with two refinements for ordinary lanes; if any lane is tiny/zero or infinite in magnitude, it maps the entire packet through scalar square root. rsqrt uses an estimate with one Newton refinement for native x86 f32 and NEON f32, true reciprocal of sqrt for x86 128/256-bit f64, and two refinements for ARM64 f64 and AVX512 f64. The iteration count is an implementation detail with observable rounding and exceptional-value consequences.

Estimate/refinement rsqrt is not interchangeable with 1/sqrt for every zero, infinity, subnormal or NaN input: intermediate products can form invalid values. The ARM64 Clang compatibility estimate helpers instead compute scalar 1/sqrt or 1/x per lane before these callers refine them, which changes rounding and exceptional-value behavior again. No uniform per-function error bound, floating-point-exception contract or cross-target bitwise result is supplied. Use the documented scalar policy facilities when their particular numerical contract is required; these packed overloads do not return per-lane error/status values.

Exponential functions

Native exp reduces by logarithm-of-two table steps, uses a small remainder polynomial, and reconstructs the power of two as two multiplications. f32 uses 16 table positions and f64 32. The protected multiplication ordering avoids prematurely overflowing an intermediate power-of-two product; this header disables unsafe reassociation locally where its compiler option abstraction applies. SIMD gathers supply the x86 table entries, while NEON extracts indices and builds a small scalar table-result array.

AVX2 and NEON preserve the original input for final special-case selection: sufficiently large values produce positive infinity, sufficiently small values produce zero, and NaNs are restored. Their f32 upper threshold is 88.72283935546875 and the f64 threshold is approximately 709.782712893384; lower cutoffs are -103.972 and -745.13. AVX512 overloads instead clamp input to their narrower 88.722/709.78 upper constants and the lower constants, then return the reconstructed result without original-input overflow/NaN restoration. Their extreme/nonfinite behavior therefore differs from the AVX2/NEON path.

exp2 computes exp(x*ln(2)), using split ln(2) for selected f64 paths. expm1 computes exp(x)-1 directly and has no separate small-x cancellation correction. There are no native packed exp10 or log1p overloads in these headers; the WebAssembly scalar-lane surface supplies additional names independently. Results do not change errno or return an overflow flag.

Logarithmic functions

Native log extracts exponent and mantissa, scales small positive values by 2^25 or 2^54, normalizes the mantissa near one, and evaluates an atanh-style polynomial before adding split logarithm-of-two terms. ARMv7 replaces vector division with a reciprocal estimate and two refinements. log2/log10 scale the natural logarithm by a constant rather than performing an independent reduction.

The implemented final selections return positive infinity for positive infinity, negative infinity for either signed zero, and quiet NaN values for negative/NaN inputs. Intermediate work is performed before these selections; masking the final result does not suppress earlier floating-point operations. Denormal handling still depends on the active hardware floating-point mode. No native log1p cancellation-specific path is supplied here.

Trigonometric and CORDIC functions

Native polynomial trigonometry reduces by pi/2 and evaluates sine/cosine polynomials, selecting signs and quadrants afterward. The x86 d256 path uses packed three-word Cody-Waite reduction while every lane has magnitude below 2^33; otherwise it reduces every lane scalarly, choosing Cody-Waite below 2^20 and Payne-Hanek above it. Nonfinite scalar-reduced lanes produce NaNs. f256 paths widen two halves to f64 before computing and narrowing the results; 128-bit x86 overloads reuse the low half of the wider path.

NEON f32 always performs scalar f64 range reduction for each lane before the packed polynomial. ARM64 f64 has a packed reduction with a large-argument scalar fallback. These choices make exceptional or large lanes affect work for the whole packet. sincos calls sin and cos separately, so it does not share their range reduction or polynomial work. tan evaluates both sine/cosine and negative-cosine/sine ratios before selecting the quadrant, which can perform otherwise unused exceptional divisions.

CORDIC variants use fixed sequences of multiply/add rotation steps with precomputed angles and powers of two. Small-input guards return x for sine/tangent and one for cosine; nonfinite inputs are selected to NaNs. The x86 f32 path again widens through f64; NEON f32 retains f32 iteration. sincos_cordic calls the separate sine/cosine variants and repeats their kernels. The names identify an algorithm choice rather than a measured performance ordering.

Sign and rounding operations

Native fabs clears the sign bit, fneg flips it, and copysign combines magnitude/sign bits where those overloads exist. This preserves the remaining representation bits rather than testing numerical negativity. Native x86 rint explicitly requests nearest-integer rounding with the no-exception immediate; it does not read the caller's current rounding-mode selection. floor/ceil/trunc select their corresponding directed modes. Native NEON's packed rint alias uses nearest-even where its vector rounding alias exists; older ARMv7 maps the scalar nearbyint helper across lanes. These paths do not provide a single current-rounding-mode contract.

A rounding name's presence does not establish a complete fenv contract, signaling-NaN behavior, exception suppression for surrounding operations, or the scalar cr policy's guarantees. Floating arithmetic can also depend on compiler contraction and target instructions; the implementation contains locally protected kernels where reassociation would change required formulas.

Four-value inverse tangent

atan2_bl_x4 reads four f64 y values and four x values, then writes four results. On AVX2+FMA it forms y/x and uses the packed rational arctangent core only when every absolute quotient lies in [2^-29,2^61). If any lane fails that test, all four are evaluated by scalar atan2_bl, including its zero/infinity/NaN/quadrant branches. Other targets always use four scalar calls. have_atan2_packed reports whether this compiled packed branch exists, not whether a particular call uses it or whether the running processor has the required ISA.

All eight input values and four output values must be addressable. Scalar fallback reads/writes sequentially, so arbitrary overlapping input/output arrays are not an advertised alias-safe conversion. atan2_pos is the positive-quadrant scalar helper and has its corresponding nonnegative-input interpretation; it is not a substitute for the full-quadrant function.

Internal register cores used by linear algebra

math/__vec_simd.hpp supplies internal __vsimd primitives for small-vector normalization, cross products, inverse matrices and related callers. It introduces no public container type. The exact reciprocal-square-root core uses sqrt followed by division, with x86 assembly preventing reciprocal-estimate substitution. The fast f32 core uses a reciprocal-square-root estimate plus one x86 or two NEON refinements. ARMv7 exact vector helpers compute a scalar result from lane zero and broadcast it, relying on the caller's splatted-input invariant.

The three-dimensional dot helper masks the fourth product before its fixed reduction tree. Cross-product padding is a subtraction of matching products and can cease to be zero for nonfinite padding. The four-lane register cores use SSE2 or NEON according to compile-time capability. Their internal names and exact/fast choices do not add a public policy type or a general packed mathematical guarantee.

Complexity, ownership and use

For a selected fixed-width register, polynomial, table and hardware kernels have bounded work and inline temporaries with no heap allocation. Mapping scalar lanes costs the sum of the scalar calls; CORDIC costs lane count times its fixed iteration count, while large-argument range reduction adds the scalar reducer's work. sincos variants currently repeat two complete calls. Wide storage, a function's name, or a vector parameter alone does not imply one instruction or a performance improvement over scalar code.

Choose these interfaces when the program already holds the admitted register type and accepts its documented backend-specific arithmetic. Select a supported width and ISA at compilation, keep any output buffers valid, and handle result-domain requirements at the caller. The functions neither resize containers nor retain raw pointer arguments, and no iterator/reference invalidation occurs except for caller-provided output memory being overwritten.

Mapping and alias

f128/f256/f512 map to f32, and d128/d256/d512 map to f64, under the corresponding architecture/feature gates. elem_t<V> aliases elem_of<V>::type. The unspecialized native primary template has no member type; it does not infer arbitrary vector-size or user packet element types. WebAssembly defines the corresponding constrained trait from its packet-traits element type.

Accepted register concept

packed_real classifies the raw register types listed in the availability section. It does not classify v128/v256/v512 wrappers or guarantee a complete mathematical overload set for every classified width. Scalar accuracy-policy classes are independent types described by the scalar math reference.

Availability

lanes_v<V> is the variable-template shorthand. Native specializations share their register feature gates and the primary template has no value member. WebAssembly computes sizeof(V)/sizeof(elem_t<V>) for its real packet/composite types. This is a logical coefficient count, independent of how many machine instructions implement an operation.
