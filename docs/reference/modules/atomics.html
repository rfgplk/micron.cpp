Atomic operations

From micron reference
micron reference › Concurrency

Atomic facilities provide compiler-builtin operations on small values, atomic pointer publication, non-owning atomic access, and a separate lock-serialized wrapper for general objects. These interfaces have different ownership and synchronization contracts.

Atomic types

TypeRepresentationUse
atomic_token<T>Aligned inline value; lock-free 1-, 2-, 4-, or 8-byte builtin operations.Counters, flags, and small publication state.
atomic_ptr<P>Inline atomic pointer; P is already a pointer type.Publishing a non-owning pointer or performing element-scaled pointer arithmetic.
atomic_ref<T>Pointer to an existing object.Atomic access to suitably aligned external storage whose lifetime is managed separately.
atomic_flagAn atomic_token<bool>.Test-and-set state or the flag protocol used by free_guard.
atomic<T>A value and an exclusive spin token.Serializing operations on a general object through its locked interface.

Memory ordering

memory_order contains relaxed, consume, acquire, release, acq_rel, and seq_cst, with corresponding memory_order_* constants. Their values are the compiler's __ATOMIC_* values. Loads cannot use release or acquire-release ordering, and stores cannot use acquire, consume, or acquire-release ordering. The templates generally pass the selected order through rather than validating these restrictions.

Compare-exchange failure is a load: the implementation changes a supplied release failure order to relaxed and acquire-release to acquire. It does not otherwise enforce that the failure order is valid relative to the success order. Overloads taking a single order derive the failure order from that order. ATOMIC_OPEN and ATOMIC_LOCKED are boolean constants false and true.

Builtin operations and target support

micron::atom supplies load, store, exchange, strong and weak compare-exchange, fetch-before and fetch-after arithmetic and bitwise operations, byte test-and-set/clear, and thread and signal fences. Raw pointers must designate live, suitably aligned objects of a type accepted by the selected compiler builtin. Atomic access does not construct the object, extend its lifetime, or make separate operations into a transaction.

For Clang on i386, the 8-byte path uses aligned storage and legacy __sync compare-exchange primitives to avoid a runtime library dependency. Its load and store use compare-exchange/exchange machinery, and weak compare-exchange uses the strong operation. These paths may impose stronger ordering than requested. Other paths use __atomic builtins; support is selected at compile time.

A bounded number of wrapper operations does not imply bounded completion under contention: compare-exchange loops can retry indefinitely. No facility here supplies hazard pointers, epoch reclamation, or protection against an ABA change of a pointer value.

micron::atomic_token

Defined in header <micron/atomic/atomic.hpp>.

An inline small value accessed through lock-free atomic builtins.

Storage and special members

Requires is_atomic_type<T>, a size of 1, 2, 4, or 8 bytes, and __atomic_always_lock_free(sizeof(T), nullptr) on the target. The public member v is aligned to at least its size and natural alignment. Default construction value-initializes it; construction from T initializes the supplied value.

The copy constructor reads o.v directly. The move constructor and move assignment directly move the value and clear the source; these are not atomic transfers. Use them only without concurrent access to either object. Copy assignment is deleted. Public v and ptr() expose the underlying object; ordinary accesses through them cannot race atomic accesses.

Operations

Complexity

Each direct operation performs one builtin operation, except for target fallback machinery. Operators combining loads do not lock both operands or provide a consistent pair of snapshots.

micron::atomic_ptr

Defined in header <micron/atomic/atomic.hpp>.

A non-owning atomic pointer with element-scaled compare-exchange arithmetic.

Template and lifetime

The template argument is the pointer type, for example atomic_ptr<int*>. value_type is that pointer type. Default construction stores null. Copying is deleted. Move construction exchanges the source with null. Move assignment loads the source, stores the destination, and then clears the source using separate atomic operations; this is not a transaction and self-move clears the pointer.

No operation deletes a pointee or keeps it alive. Dereference and arrow first load a pointer, then access its object. Pointee lifetime and synchronization of the pointed-to contents remain the caller's responsibility.

Operations and complexity

load, store, exchange, expected-reference compare-exchange, assignment, and pointer conversions provide the corresponding atomic pointer operation. Pointer increment, decrement, and compound addition/subtraction use a weak-CAS retry loop with acquire-release success and relaxed failure. They compute old + n or old - n as C++ pointer arithmetic, so n counts elements and the resulting pointer must remain valid within its array object.

Nonmutating arithmetic performs a snapshot load. Pointer subtraction returns usize; a negative difference is converted to an unsigned value. Comparing two wrappers uses two independent loads. Direct load/store/exchange operations use a constant number of builtin calls; arithmetic retries have no bounded completion time.

micron::atomic_ref

Defined in header <micron/atomic/atomic.hpp>.

A non-owning atomic access wrapper referring to one existing object.

Construction and access

Construction stores the address of a supplied T&. Requires an atomic type and a trivially copyable T; the constructor performs no alignment or lock-free assertion. The referent must remain live and suitably aligned for the selected builtin until the wrapper and all operations on it are finished. Construction uses &obj, so an overloaded address operator affects that expression.

Provides load, store, exchange, strong compare-exchange, prefix increment/decrement, arithmetic fetch-add/subtract, comparisons, and snapshot arithmetic. These affect the referred object rather than a copy. value_type is T. Copying is explicitly deleted and no move operation is provided. The wrapper neither allocates nor destroys the referent.

Complexity and synchronization

Direct operations perform one builtin call. Every conflicting concurrent access to the same storage must use a compatible atomic protocol. Creating a wrapper does not convert subsequent ordinary accesses to atomic accesses.

micron::atomic_flag

Defined in header <micron/atomic/flag.hpp>.

A non-copyable atomic boolean supporting test-and-set and polling.

Operations

Default construction clears the public token tk. test(order) loads it, test_and_set(order) exchanges true and returns the old value, and clear(order) stores false. ttas(success, failure) waits with acquire loads and pause backoff, then retries weak compare-exchange until acquired.

wait(old, order) ignores order: it repeatedly uses relaxed loads and yield() while the value equals old. It has no futex registration or corresponding notify operation. A return from this wait alone supplies no acquire publication edge; perform the required acquire observation separately. It waits for a changed value, not for a notification.

The direct operations have constant wrapper work. ttas and wait can wait indefinitely and require another execution context to change the state.

micron::atomic

Defined in header <micron/atomic/atomic.hpp>.

A general value wrapper whose ordinary operations serialize through an exclusive spin token.

Locking and object lifetime

Stores a T and an atomic_token<usize> lock. Ordinary mutation, comparison, conversion, and arithmetic acquire the token using sequentially consistent compare-exchange, compute or copy a result, then unlock. These interfaces require the corresponding T operation to be well-formed; they are not hardware atomic operations on T.

Copy and move construction directly access the value and token without locking either object. No wrapper-to-wrapper assignment operation is provided. They require exclusive access. Copying a held token also copies the held state. Most ordinary operations manually unlock after the T operation; if it throws, the token remains held. Reentrant operations on the same wrapper deadlock.

Protected access

MemberDescription
operator->()Acquires the token and returns an immovable temporary locked view. Its destructor unlocks at the end of the full expression, or when a retained view leaves scope.
get()Acquires the token and returns T*; the caller must eventually call release().
release()Unlocks the token. It does not destroy or transfer the value.
__get, __store, compare_exchange_*Apply compiler atomics directly to the stored value and bypass its spin token. They require a builtin-compatible T and do not serialize with ordinary locked operations.

Complexity and use

Storage is inline. An uncontended wrapper operation adds a constant number of atomic operations to the cost of its T operation. Contended acquisition can wait indefinitely. Retained pointers or references from a view must not be accessed after the view releases its lock. Use a single consistent interface to protect the value.

Example

#include <micron/atomic/atomic.hpp>

int main()
{
  micron::atomic_token<int> value(2);
  value.fetch_add(3, micron::memory_order_relaxed);
  return value.get(micron::memory_order_relaxed) == 5 ? 0 : 1;
}
