SIMD

From micron reference
micron reference › SIMD

Raw register aliases, fixed-size SIMD packet classes, intrinsic wrappers and bounded buffer operations selected by target architecture and enabled instruction-set features. Register width, lane interpretation and the available operation set are separate properties; the implementations do not provide a uniform container or arithmetic interface across every target and width.

Compile-time selection

The dispatcher headers choose their architecture implementation through __micron feature macros. The reviewed simd/types.hpp has x86, NEON and WebAssembly branches and otherwise emits a preprocessing error; it supplies no general scalar architecture backend. WebAssembly's storage fallback belongs to its explicit target branch. Individual raw x86 intrinsic definitions carry target attributes, but a program using an operation must still supply a compatible compilation and execution target.

dispatch.hpp additionally defines internal hosted-x86 CPUID/XCR0 query helpers. They return feature fields and OS AVX-state eligibility; they do not automatically select implementations for the public wrappers. __has_sse requires the entire listed SSE through SSE4.2 feature set, and __has_avx256 tests AVX2 plus OS state. The native operation interfaces contain no automatic runtime width dispatch.

intrin.hpp supplies its own intrinsic definitions and defines vendor intrinsic-header guards. MICRON_SIMD_INJECT_INTRIN_TYPES and MICRON_SIMD_INJECT_INTRIN_SYMS are defined by default here, and the injection condition tests whether the macro is defined rather than whether its value is nonzero. Defining either as 0 therefore still enables its associated injection. Include-order and compiler compatibility matter when combining this surface with other intrinsic headers.

Register values, lanes and construction

A raw integer register is an object representation. The lane suffix of an operation selects signedness and 8/16/32/64-bit interpretation; it does not numerically convert all possible views. Packet templates pair a raw register type with a scalar flag F. The canonical aliases use signed integer flags or f32/f64. The raw-register and flag concepts do not enforce every meaningful register/flag pairing; availability of a declaration does not establish a working implementation for an arbitrary admitted pair.

Packet objects contain inline register storage, default to zero and retain no pointer ownership. Their natural-order scalar constructors place argument zero in lane zero. This differs from vendor-style set functions whose ordinary set_* argument order is high lane first and whose setr_* order is low lane first. Wrong-length native initializer lists construct zero packets; NEON initializer-list assignment with the wrong length leaves the existing value unchanged.

Several integer scalar constructors and setters choose broadcast width from the argument's type rather than F. Scalar arithmetic also differs by width: the x86 128/256-bit += paths convert to F, whereas their -= paths dispatch on the argument type; the 512-bit scalar paths likewise use argument-type width. Use an explicitly matching scalar type when lane grouping must be preserved. Unsupported floating/scalar pairings can leave a value unchanged rather than converting it.

Packet ownership and mutation

Copying copies inline bits in constant work for a fixed width. Move construction zeros the source for native 128/256/512-bit classes; move assignment also zeros it for x86 256 and NEON, but x86 128/512 move assignment leaves the source bits present. No move transfers an allocation. Destruction releases no external memory. Every arithmetic or shuffle mutation overwrites only the packet's own storage, and a store overwrites the caller's destination.

size and indexing are not a uniform range interface: native 128/256-bit implementations provide selected lane access, ARM size/index members are non-const, and native v512 deletes subscript access and supplies a smaller member set. A packet has no capacity, append, resize, iterator ownership or allocator policy. References into packet storage, where obtainable, remain tied to that object's lifetime and can observe later overwrites.

Loading, storing and address requirements

Native x86 packet load checks full-register alignment and silently retains the previous packet when the address is misaligned; uload performs a full-width unaligned load. The corresponding aligned raw load/store functions assume alignment without checking it. NEON packet get uses the ordinary memory operation, and WebAssembly packet transfers use byte copies without the x86 alignment gate. All full-width accesses require the complete width to be addressable, even when only some resulting lanes are subsequently used.

The common raw load dispatcher implements 128/256-bit x86 and 128-bit NEON paths; inclusion of b64 or native ARM composite records in a type concept does not add missing load overloads. Partial low 2/4/8-byte loads zero the remaining bytes. Low/high-half loads preserve the other half as specified by their operand. Broadcasts read one scalar value, while explicitly named low-lane insertion is not necessarily a splat: sse::broadcast_i32_to_i128 and broadcast_i64_to_i128 insert the scalar low bits and zero the rest.

Native NEON masked-load wrappers first load the entire 128-bit block and then clear inactive lanes. Their mask does not make inaccessible inactive addresses valid. Gather wrappers select indexed lanes and require every active computed address to be valid; no bounds checks or allocation occur. x86 gather scale is an immediate 1, 2, 4 or 8, and WebAssembly enforces the same set. Native NEON helpers accept their scalar byte scale directly. Negative signed indices are meaningful only when the resulting address remains within caller-owned readable storage.

The x86 gather_64_i32 and gather_pd_i32 overload sets include matching parameter signatures distinguished by their return width; an ordinary call cannot select a width from the assignment destination. gather_pd_i64 also uses a real-register index parameter where the underlying operation expects integer indices. These declared combinations are incomplete interfaces rather than a general overload-resolution or numerical index-conversion facility.

Arithmetic width limits

Packet integer multiplication is implemented for 16/32-bit lanes in native 128/256-bit paths. Eight-bit and 64-bit variants have missing or rejecting branches, and a native 128-bit scalar 64-bit multiplication branch can fall through to a default zero result. Native v512 scalar multiplication supports 16/32 bits and 64 bits with AVX512DQ; it does not acquire the full 128/256-bit member interface. Native NEON free arithmetic rejects some 64-bit multiplication combinations even where a lower-level ARM64 helper exists.

NEON hadd/hsub and x86 horizontal names are not interchangeable algorithms. The former compute halved lane-wise sums/differences; the latter combine adjacent lanes. NEON select uses mask bits rather than converting a scalar Boolean. Signed arithmetic implemented with compiler compatibility scalar expressions is subject to those expressions' overflow restrictions, so wrapping behavior cannot be assumed for every low-level compiler fallback solely from an intrinsic-style name.

Mask and zero-test notes

Packet comparison results are integer encodings, not Boolean packets or a cross-width mask type. In particular, a 256-bit byte comparison and a 128-bit NEON byte comparison do not preserve a separate result for every byte. Native x86 256-bit floating != uses an ordered predicate, so NaN lanes compare false; native 128-bit x86 and NEON use inverted equality and yield true for NaNs. Native v512 has no separately implemented != member matching the smaller classes.

For native x86 128/256-bit and NEON floating packets, all_zeroes/all_ones inspect sign bits rather than every representation bit. A packet of positive nonzero floats can satisfy all_zeroes, and all-negative floats can satisfy all_ones. Integer checks, native 512-bit checks and WebAssembly checks use the corresponding bit tests. to_ones writes every representation bit as one, producing NaN representations for real lanes rather than numerical one.

Scalar AVX512-style __mmask values use one low-order bit per lane; high unused bits have no corresponding lane. Merge forms preserve src in inactive lanes, while maskz forms write zero. Many NEON masked math/shift helpers compute all lanes and then blend; masks do not suppress inactive floating operations or establish a floating-exception predication guarantee. Scalar _ss-style inactive NEON forms return the whole src or whole zero value, whereas active upper lanes follow their a operand.

Shifts, rotations and permutations

Families include immediate/common-count/per-lane logical shifts, signed arithmetic shifts, byte shifts, rotates, double-width funnel shifts, lane extraction/insertion, zip/unzip/transpose, table lookup, blends and byte shuffles. x86 byte-shift counts are template immediates; NEON wrappers take runtime int counts. Wide x86 byte shifts and several permutations remain local to each 128-bit block. The common x86 count operand reads its low 64 bits, while native NEON wrappers narrow the scalar count through int.

Per-lane 16-bit shifts require AVX512BW+VL in the relevant x86 wrapper; arithmetic 64-bit shifts and rotates require AVX512F+VL, and the double-shift family is gated by VBMI2/BW/VL even for the described wider forms. These declared wrapper sets also call intrinsic names not uniformly implemented by the compatibility layer; a visible template is not a guarantee that every admitted instantiation compiles.

Native NEON rotate/funnel formulas do not uniformly reduce counts modulo lane width. Keep rotate counts in [0,width) and funnel counts within the implemented valid width range; negative or excessive counts can reach undefined C++ shift expressions. Some low-level vshl operations instead interpret negative counts as a reverse-direction shift. Native NEON packet alignr leaves the packet unchanged for immediate counts at least 16, differing from x86 concatenation semantics.

PSHUFB-style packet shuffles use each byte's low index within its 128-bit block and clear bytes selected by a set high mask bit. The neon::tbl family instead clears out-of-table indices, including indices at least 16 for a one-register table. These are distinct indexing contracts. Low-level immediate lane selectors must be compile-time constants within the target intrinsic's lane range.

Floating-point operations and rounding

The ordinary native x86 surface supplies arithmetic, min/max, sqrt and selected reciprocal/reciprocal-square-root estimates, rounding and conversions. The 128/256-bit f32 rcp/rsqrt intrinsics are hardware estimates without automatic refinement. Native 512-bit rcp14/rsqrt14 names use their corresponding estimates. x86 min/max select according to their instruction's operand/unordered rules; Clang compatibility elementwise min/max can differ on NaNs and signed zeros.

Native NEON f32 division uses reciprocal estimation with two refinements on ARMv7; ARM64 uses vector division. NEON ordinary reciprocal/rsqrt wrappers use their stated refinement count, and the 14 variants add a second refinement for f32. ARM64 f64 14 wrappers use scalar reciprocal or reciprocal of square root per lane. ARMv7 raw vector sqrt uses reciprocal-square-root refinement with special zero selection; the separate low-level neon::sqrt helper uses scalar VFP lane square roots. These interfaces are distinct from math::mk packed polynomial kernels.

Expanded transcendental/complex x86 aliases are largely behind __micron_simd_svml and require their external implementation surface. Ordinary inclusion does not supply a complete exp/log/pow/cbrt/hypot/complex intrinsic library. Native NEON math wrappers implement many such names by extracting lanes and calling mkbits scalar kernels; a vector signature need not mean a packed polynomial or one machine instruction.

The low three round-control bits encode nearest, floor, ceil, truncation and current direction. On native ARM64, nearbyint and rint do not share a single convention: directed aliases and the scalar fallback follow their actual implementations; Clang compatibility rint/nearbyint use nearest-even in the reviewed code. Embedded-rounding arguments and exception-suppression bits are ignored by selected compatibility wrappers. No uniform signaling-NaN, exception or current-rounding-mode guarantee follows from the name alone.

Multiply-add and numerical masking

x86 fma(a,b,c) computes a*b+c, with the associated fmsub/fnmadd/fnmsub and alternating add/sub forms. NEON aliases use accumulator-first order: fma(a,b,c) computes a+b*c. ARMv7 paths without the fused instruction compute a separate multiplication and addition, with two rounding steps. x86 packet FMA wrappers cover 128/256-bit packets by reinterpreting their single-register layout after a sizeof assertion; they do not define a native 512-bit packet FMA interface here.

Native NEON masked reductions replace inactive floating lanes by finite +/-maximum values rather than infinities. For min/max reductions this can alter an all-infinite active result, and an empty active mask yields the finite sentinel. Masking a final value does not undo intermediate exceptional arithmetic. Programs requiring bitwise agreement, exception suppression or a specific rounding model must use the actual backend contract rather than translating names between architectures.

Scalar bit and cryptographic helpers

The bmi aliases provide trailing/leading-zero counts, low-bit isolation/reset/mask, bit extraction/deposit, bit-field extraction, high-bit clearing and widening multiplication. Zero counts return the operand width for zero. Portable pext/pdep fallbacks iterate selected bits, taking O(popcount(mask)) work rather than constant work in mask density. widen_mul returns the low half and writes the high half through a valid output pointer. Keep high-bit-clear indices within the operand width for consistent native/fallback behavior: the native instruction narrows its control field while the portable branch compares the full argument.

AES and carryless-multiply wrappers expose instruction steps, not complete ciphers, modes, key schedules or authenticated encryption. x86 enc_round includes MixColumns and round-key xor; ARM vaese excludes MixColumns and uses a different key-xor position, with separate mix_columns helpers. Equal-looking round names therefore cannot be substituted directly. Carryless multiplication selects 64-bit halves and returns their 128-bit polynomial product. Native ARM AES/PMULL/CRC and x86 crypto paths have their own feature requirements and do not supply a general software cryptographic fallback.

Population-count wrappers use a SWAR fallback when the hardware feature is unavailable. Prefetch and fence wrappers expose their target's operation, with WebAssembly prefetch implemented as no operation and its fence helpers using compiler atomic fences. A prefetch is not a bounds check, ownership operation or portable cache flush.

Memory operation parameters and results

Typed memcpy/memmove/memset/memcmp families take an element count and form a byte count from count*sizeof(T); that multiplication is unchecked in native implementations. Pointer arguments carry nonnull requirements even where a zero count would make a loop empty. memcpy requires nonoverlap and a valid trivially copyable object representation. memmove chooses forward/backward copying for overlap. Byte-pattern setting does not invoke T constructors or perform element assignment.

memcpy/memmove return the destination, and mempcpy returns destination+count. The word-setting family repeats the native u64 representation across the specified bytes. rmemcpy copies count*sizeof(D) bytes under its own signature; it has no implicit destination-capacity check and no general construction/lifetime management. memcmp returns zero for equal byte sequences and otherwise the signed difference/order of the first unequal unsigned bytes; it is not element-wise operator<.

memchr/memrchr/memmem scan bytes. Their returned T* can designate an address that is not aligned to a T boundary, and selected overloads remove constness in the returned pointer. They must not be treated as typed element lookup or permission to mutate an originally const object. The empty needle matches the beginning, and failed searches return nullptr. No operation retains a pointer, allocates output storage or manages a container's length.

Memory alignment, work and storage

Copy, move, set, compare and byte scans take O(byte_count) work and O(1) temporary storage; comparisons/searches can stop early. The substring search can take O(haystack_bytes*needle_bytes). Aligned variants assume 16/32/64-byte alignment according to their selected width. x86 256-bit memory routines can use pairs of SSE transfers when AVX2 is absent; explicitly 512-bit routines require their AVX512 features. Native NEON exposes 128-bit names, while WebAssembly's width-labelled entry points forward through its common byte algorithms.

Non-temporal x86 stores require their aligned destination and issue the corresponding store fence. ARMv7 paths use ordinary stores plus dmb st; ARM64 paths use paired non-temporal STNP stores plus dmb ishst, with ordinary tail stores. These are implementation choices, not a general promise of cache bypass or better throughput. Internal bulk-copy assembly blocks have minimum-large-size preconditions and unconditional head/tail accesses; they are not general replacements for the public small-copy dispatcher.

ARM64 bulk zeroing can inspect DCZID and use an enabled 64-byte DC ZVA block operation. That localized cache-zero capability check does not turn the public SIMD arithmetic selection into runtime ISA dispatch. WebAssembly byte-count helpers trap on their checked overflow path, unlike the native unchecked product.

Buffer algorithm notes

Extrema use AVX2 for selected i32/u32/f32/f64 inputs, ARM64 NEON for selected integer widths and real types, ARMv7 NEON for selected i32/u32/f32 inputs, and scalar paths otherwise. The scalar base case for zero elements returns an index that does not designate an element. Bitonic sorting accelerates selected integer/floating types with AVX2 or NEON and falls back scalarly; a non-power-of-two count can index outside the input. Floating compare-exchange min/max can replace or reorder NaN representations rather than preserving a permutation contract.

The native x86 char byte-scan tails compare an unsigned byte directly with their char parameter. On a target with signed char, a search byte at least 128 can match full vector blocks but fail in the scalar tail. Native NEON normalizes that byte parameter to unsigned. These helpers therefore do not currently offer uniform arbitrary-high-byte behavior across all block positions.

Bounded string and code-unit operations

simd/strings.hpp supplies first/last occurrence, count, membership scans, substring lookup, lexical comparison, ASCII lower/upper conversion, reversal, copying and cyclic xor transforms over pointer/length storage. Intended code-unit sizes are 1/2/4/8 bytes, with selected NEON paths scalar for 64-bit units. Returned failed-search positions use the supplied length; an empty substring matches at 0. Lexical comparison returns order by the first differing unit and then length. No operation decodes UTF-8, combines code points, performs locale case folding or allocates a terminated string.

Linear scans/conversions/reverse cost O(n) time/O(1) storage; membership costs O(n*k) for k candidate units and substring matching can cost O(h*n). Count means code units rather than bytes unless the function explicitly scans bytes. Although some templates admit types by size alone, floating code units can compare by SIMD representation in blocks and by scalar == in tails, giving differences for signed zeros or NaNs. Use integer character/code-unit types for consistent textual equality.

The unbounded sse_strlen helper aligns then reads whole 16-byte blocks. The complete block containing the terminator must be readable; a terminator does not limit that load to preceding bytes. Bounded routines keep their documented pointer/count preconditions. Cyclic xor with a zero-length second input copies the first input, rather than indexing or allocating a repeated empty key.

Compiler compatibility limits

The local Clang compatibility headers implement many vendor-like operations using scalar lane loops or compiler vector expressions. Some mask/rounding wrappers discard mask, passthrough or rounding arguments; gather helpers test a lane for nonzero rather than always using the native sign-bit rule. These wrappers are not a complete vendor intrinsic emulation, and wrapper names alone do not establish inactive-lane exception behavior or instruction-level equivalence.

Selected 128-to-256 cast helpers iterate the destination lane count while indexing the smaller source, so their upper-lane accesses are not a defined zero-extension. Use a specifically implemented zero-extension operation when that contract is required. Selected Clang 512-bit logical-right-shift fallbacks first convert a signed narrow lane to unsigned long long, which retains sign-extension bits before shifting; high-bit inputs can therefore differ from a lane-width logical shift.

ARM64 Clang reciprocal-estimate compatibility helpers compute exact scalar 1/x or 1/sqrt(x) per lane before callers apply refinement, giving different exceptional/rounding behavior from hardware estimates. Other low-level ARM compatibility paths contain scalar overflow-sensitive expressions or generated immediate-assembly forms with limited usable instantiations. The reference describes these current limits rather than promising that every declared vendor-style combination is supported.

Choosing an interface

Use raw aliases for an explicitly supported target instruction or register layout, packet aliases for their implemented fixed-value member operations, and bounded memory/string algorithms when the data already lives in caller-owned contiguous storage. Select lane width and signedness deliberately, match load/store alignment and fully address every accessed lane. Wide composites are useful storage representations where native wide instructions do not exist, but their width is not a throughput guarantee.

Register operations have bounded work and inline storage for each fixed width. Pointer/count operations state their count-dependent work above and retain no references or allocation ownership. There is no universal performance ordering among widths, packet/raw wrappers, estimate/refinement or scalar-lane fallbacks; workload length, target ISA and the actual selected implementation determine the relevant costs.

Representation and use

Members and constraints

The class stores one raw register and implements its supported constructors, setters, full/unaligned load/store, scalar lane access, comparisons, arithmetic, bitwise operations and shuffles. Operations follow the lane flag but their implementation sets differ for integer widths and real types. Native x86 bit_width/lane_width aliases are public; native NEON declares those aliases before its public section. Hence the structural is_neon_simd_class concept does not recognize the canonical NEON packet solely from those private names.

Results and lifetime

Default construction zeros all bits; returned packets own their value and retain no source pointer. The comparison-mask encodings, sign-only floating zero tests, x86 aligned-load no-op, argument-type scalar broadcasting and move-source differences are described above. Native v128 has no general public conversion to or constructor from its raw register. Free wrappers passing the packet directly to raw intrinsics can therefore be unusable despite accepting it in a concept.

AVX512F gates alias declarations, while individual integer 8/16-bit operations need BW and 64-bit multiplication needs DQ. Value semantics

Storage is inline. Move construction clears the source while move assignment preserves its bits. Full-width transfers require 64 addressable bytes and the corresponding alignment where requested. No generic dynamic resizing or per-lane exception/status storage is provided.

Classification

The concept checks exact type equality with the defined 128-bit aliases, enabled 256-bit aliases and, only under __micron_simd_wide_composite, 512-bit aliases. It is not a structural test of arbitrary packet-like classes, does not remove qualifiers, and currently omits native AVX512 z aliases. A successful concept test also does not prove that a particular free wrapper can convert the packet to a raw intrinsic operand.

micron::simd::__wasm_storage

Defined in header <micron/bits/wasm/simd/types.hpp>.

Inline aligned lane storage used by the explicit WebAssembly SIMD type route when its native 128-bit carrier is unavailable.

Storage and composites

__wasm_lanes<F,N> holds a scalar lane array. __wasm_storage<F,Bytes> has alignment min(Bytes,16) and its fixed lane array; __wasm_native selects a 16-byte compiler vector in the native-vector branch. __wasm_composite<B,N> contains N blocks with 16-byte alignment and supplies the raw 256/512-bit aliases. __wasm_packet_traits exposes the element type and byte width for recognized raw storage. None of these types owns dynamic memory or implies a native wide instruction.

Packet alias implementation

__wasm_vector<B,F> owns the inline bits used by v128/v256/v512 aliases and implements many operations by copying to a scalar lane view, applying lane formulas and packing the result. Integer wrapping arithmetic explicitly uses unsigned representations where implemented; integer division still requires a nonzero divisor and a representable signed quotient. Float and integer mask encodings differ as stated above. Full transfers use byte copies, comparison masks and all-bit tests follow this backend, and byte permutations are local to 128-bit blocks.
