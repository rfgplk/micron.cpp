Memory operations

From micron reference
micron reference › Memory management

Memory operations copy, move, fill, compare, and search caller-provided ranges. Their counts have API-specific byte or element units. Raw storage operations do not infer destination capacity, construct arbitrary nontrivial objects, or synchronize concurrent accesses.

Headers and count units

<micron/memory/cmemory.hpp> includes copy, move, fill, compare, search, and selected SIMD memory names. <micron/memory/memory.hpp> adds string operations and common types. <micron/mem.hpp> includes object/category operations from memory/actions.hpp; it is not the complete C-style memory umbrella.

The pointer arguments must designate suitably aligned, accessible storage of the required extent. A zero count does not cancel declaration-level nonnull requirements on overloads carrying that attribute. Except for interfaces with explicit bounds, the implementation does not infer allocation lengths. Counts multiplied by a type size must fit the unsigned byte-count type.

Copying and moving

memcpy<F, D>(destination, source, count) returns the destination. At runtime, equal-sized trivially copyable F and D select representation copying. Otherwise each destination element is assigned static_cast<F>(source[i]). In constant evaluation the ordinary constexpr function always uses element conversion. Consequently copying equal-width integers into floating-point objects can copy bits at runtime but convert numeric values in constant evaluation. constexpr_memcpy always uses converting element assignment and is constrained to fundamental element types.

Ordinary memmove uses the same runtime representation/conversion distinction and selects forward or backward copying for overlap. It is not declared constexpr; the separate fundamental-type constexpr_memmove performs direction-aware converting assignment. Converted element movement requires compatible pointer comparisons and valid destination objects; it is not placement construction. In particular, different source/destination element layouts do not acquire a general arbitrary-byte-overlap guarantee from a converting loop.

bytecpy and voidcpy copy exactly the requested bytes. bytemove moves that many bytes with overlap handling. There is no ordinary micron::memcpy(void*, const void*, count) overload in this implementation; use voidcpy for that signature. The fundamental-pointer byte helpers and their reference variants require valid underlying byte ranges even when their exposed type is wider. Writing through a helper that casts away constness is valid only when the actual destination is mutable.

Copy routines use restrict-qualified ranges and require nonoverlap. The shallow/fresh copy interfaces have the same restriction. Use an appropriate move interface for overlapping representations. mempcpy has copy semantics and returns destination + count. r* variants usually take the address of the supplied first object and return a reference; that reference does not prove the following range exists.

The c* forms take the count as a template argument; this makes the count known to compilation without turning all functions into constant-expression operations. constexpr_bytecpy has a distinct constant-evaluation branch that assigns only count / sizeof(F) whole elements and omits a partial trailing element; it is not a general representation-preserving byte copy in constant evaluation. Some constexpr_* byte helpers still use reinterpret casts whose validity in a constant expression is restricted by the language.

Complexity is linear in the number of bytes or converted elements processed, with constant auxiliary storage. Same-address/zero-count move shortcuts perform constant work. These memory functions are noexcept; throwing user-defined conversion or assignment does not propagate as a recoverable exception from them.

Filling and element transforms

memset, byteset, and bset repeat a byte value over a byte count and return the original destination. Template-count cmemset/cbyteset, template-value forms, and their reference variants retain that byte-count interpretation. The ordinary fixed-width _8b, _16b, _32b, and _64b fill helpers issue u64 stores directly and require suitable 64-bit alignment and accessible complete widths.

typeset<T> repeats a T representation for types of size 1, 2, 4, or 8 bytes, using a repeated word pattern, and uses T assignment for other sizes. Its exposed destination pointer type does not select a conversion to that pointer's element type. The caller must ensure that these writes are appropriate for the destination's objects and representation. wordset repeats a word pattern over the requested word count.

zero and rzero clear count * sizeof(F) representation bytes. constexpr_zero assigns zero to elements. full/cfull fill every representation byte with 0xFF at runtime but assign the numeric value 0xFF to each element during constant evaluation. The ordinary fixed-element full_4/full_8/full_16/full_32 helpers also assign 0xFF per element; a wider integer therefore receives 255, rather than every bit set. set uses the type's complement-of-zero expression, and clear assigns zero.

cbyteset in constant evaluation assigns whole elements only. Integral elements receive a repeated-byte integer pattern; nonintegral elements receive F{} regardless of a nonzero requested byte. A remaining partial element is not written. These branches differ from the runtime byte fill, so representation-sensitive work should use a valid runtime byte interface or explicit element operations.

one/low_bit, pattern, alternating_aa, alternating_55, high_bit, and mask assign a numeric value per element. mask assigns its argument; and_mask, or_mask, and xor_mask modify existing bits. invert/not_, increment/decrement, and add/sub transform each existing element. memfrob XORs each element with 0x15 and returns the original pointer. Arithmetic and conversion retain the selected element type's ordinary constraints, including signed-overflow restrictions.

Each fill or transform is linear in its processed range with constant auxiliary storage. Byte-pattern writes do not invoke destructors or user constructors. An all-zero or all-ones byte pattern is not automatically a valid value for every C++ type.

Checked and volatile-store variants

An s prefix has different meanings across these families. smemcpy, sbytecpy, svoidcpy, and the corresponding move forms reject null and failed alignment checks, returning null or false, but do not check source or destination capacity. Fill and comparison s* forms additionally use an address-membership helper. That helper accepts estimated stack ranges or backend-known heap ranges; its heap branch does not verify the entire requested extent. Mapped, static, foreign-heap, or valid subranges can fail this heuristic, and membership does not prove object lifetime or readable/writable bounds.

For typed fill/compare families, the membership helper is frequently passed the element count rather than its byte product. Several reference-checking overloads pass the referenced value to pointer-oriented alignment/address helpers and do not instantiate for arbitrary scalar references. Their names are not a guarantee that every reference type accepted by an unguarded overload is supported. Alignment values used by unchecked modulo-based helpers must be nonzero.

scmemset, scbyteset, scbzero, sctypeset, scwordset, and appropriate zero/full forms use volatile destination stores and a trailing barrier to retain writes. These operations are distinct from the *_safe checked forms; a volatile-store form does not itself validate null or capacity. The implemented barrier is an ARM32 dmb ish or a compiler barrier on the other branches, not one universal hardware synchronization operation.

The reference rscfull implementation writes through the ordinary reference rather than a volatile pointer, unlike pointer scfull. Do not infer identical guaranteed-write behavior from the shared prefix. None of these variants supplies mutual exclusion, atomic element access, or a general concurrent zeroization protocol.

Comparison and equality

memcmp<T>(left, right, count) requires the selected comparison type T; it is not deduced from the F* parameters of that overload. With one-byte T, comparison is lexicographical over unsigned byte values. With wider T, the scalar loop uses != and < and returns minus one or one at the first unequal element. Reinterpreting a different pointer type as T also requires valid alignment and object access. For floating types, unordered comparisons follow the actual scalar expressions rather than a total ordering.

bytecmp/bcmp compare byte ranges. typecmp<T> compares count * sizeof(T) representation bytes; wordcmp similarly compares representations. Representation ordering depends on byte order and can inspect padding, and is not numeric element ordering. Runtime and constant-count/constant-evaluation variants can return different nonzero magnitudes; use the sign only where the selected routine implements value ordering.

The fixed-width memcmp_8b/16b/32b/64b, matching bytecmp_*/bcmp_*, fixed-word wordcmp_*, wider-T smemcmp variants, and rscbytecmp_safe do not implement normal mismatch ordering: their mismatch paths subtract the addresses of the two compared positions. Subtracting pointers into separate arrays is not a valid C++ value-ordering operation. These helpers should not be used as ordering comparators. The ordinary byte dispatcher and scalar memcmp<T> have distinct, value-based mismatch paths.

Comparison s* routines return the minimum i64 value when their null/alignment/address check rejects an input. This sentinel must be handled separately from a negative ordering result. Their heuristic checks do not make comparing an arbitrary address safe.

Without a predicate, compare_range and compare_n use byte-representation comparison. Container compare_range compares the common prefix and uses lengths to break a tie; container compare_n clamps to the smaller available range and does not break a prefix tie by length. These default container bodies assume that begin() identifies contiguous storage, even though the iterable concept alone is broader.

Predicate overloads instead require each visited pair to satisfy the predicate and return a boolean. Whole-container compare_range first requires equal lengths. Bounded container predicate comparison stops after at most n pairs or either end and can succeed for equal prefixes of different lengths. Pointer overloads rely on the supplied count/range. Predicates can take values or pointer pairs, selected by the overload/template form; a callable matching multiple forms can require explicit disambiguation.

Worst-case comparison work is linear in examined bytes/elements and stops at the first mismatch. No constant-time-in-the-security-sense comparison is supplied; execution can reveal prefix agreement.

Search operations

memchr returns the first matching element, memrchr the last, and memmem the first equal subrange. A null searched range returns null. memmem returns the haystack for an empty needle when the haystack is nonnull, rejects a null nonempty needle, and rejects a needle longer than the haystack. Counts are T elements, with SIMD dispatch for byte-sized types and scalar element comparisons for wider types.

The pointer overloads return mutable T* even when passed const T*; the cast does not grant permission to modify an actually const object. The unusual reference memchr(const T&) body combines indexed source access with a T* result and can fail instantiation for scalar or pointer-reference substitutions; use the pointer overload with a valid element type.

Character search is linear in the searched length in the worst case. The scalar subrange search performs candidate-by-candidate comparisons and can require the product of haystack and needle lengths. SIMD filtering changes the implementation path, not a documented universal throughput or sublinear worst-case guarantee. Search does not allocate or alter the searched objects.

Memory dispatch and tuning

Ordinary byte copy/move/fill uses short head/tail ladders through 128 bytes, or through 256 bytes when AVX2 is compiled. These helpers load/store within the requested byte span; short move loads the necessary source pieces before writing destinations. Larger spans use the selected SIMD memory backend, a suitable string-instruction route, or a non-temporal route.

On x86, transfers below the 2048-byte large-path threshold use bulk routines. Larger calls consult shared tuning thresholds. A hosted first use can perform a one-time CPUID probe for ERMS/FSRM and last-level-cache information; concurrent first users wait for publication. The probe tunes thresholds and does not authorize instructions beyond the compiled backend. Freestanding startup can call __micron_mem_init; without published tuning, the default thresholds remain available.

MICRON_MEM_NO_PROBE omits the runtime probe. MICRON_MEM_NT_THRESHOLD defaults to 16 MiB and supplies the fallback non-temporal thresholds. With detected cache information, copy and set thresholds are independently derived from cache size with a 1 MiB floor. Rep-move/set thresholds also depend on detected string-instruction features and are capped by their non-temporal threshold. An internal route-info helper reports the selected cutovers.

The AArch64 byte paths use an 8 MiB non-temporal cutover; zero fill can select the zeroing backend from 256 bytes. Other architecture branches use their compiled bulk routines. Large overlap move chooses a backward path when the destination starts inside the source at a greater address; non-temporal copy routes are restricted to disjoint ranges.

cmemory.hpp re-exports SIMD-width names from simd, including selected aligned, non-temporal, copy/move/fill/compare/search/word variants. They retain the SIMD module's alignment and ISA requirements and are not aliases that make arbitrary input aligned. Use ordinary dispatching functions unless a caller can satisfy the specific primitive's requirements.

cache_line_size, constructive interference size, and destructive interference size currently return a fixed 64-byte value on every branch. They do not probe cache geometry. The implementation details above explain route selection; they do not establish a benchmark advantage for any workload.

Experimental unrolled operations

The separately included cmemory/__unroll_memcpy.hpp and __unroll_memset.hpp define micron::experimental versions. Template-count operations expand index sequences; copy uses converting element assignments, whereas fixed byte-copy helpers copy their stated byte width. Unroll-copy expansion is bounded by the 1024-byte threshold for selected templates, but many fill forms expand their entire template count.

These are separate implementations and can differ from ordinary dispatch semantics. Experimental full assigns 255 per element rather than using the ordinary runtime all-0xFF representation fill, and experimental memfrob returns the advanced end pointer rather than the original pointer. The _32 copy switch handles byte lengths zero through 32 and returns unchanged for a larger supplied length.

Large index-sequence expansions can greatly increase compile work and generated code. The source does not justify a general speed claim over the ordinary short ladders or bulk routines. They retain caller bounds, lifetime, overlap, and checked-family limitations.

Object construction and transfer

move, forward, and forward_like change expression category; they do not themselves allocate, move object state, or end an object's lifetime. swap uses a temporary and move assignments under its declared copy/move constraints. exchange moves out the old value and assigns the replacement. reset keeps the old moved value in a temporary while assigning a replacement; it does not reconstruct the original object in place.

construct and construct_at placement-construct an object at supplied storage with forwarded arguments. The reference form uses the referenced object's address and requires the caller to have arranged a valid storage/lifetime transition. destroy and destroy_at ignore null and invoke only the destructor; they do not release allocation storage. The placement operator new/new[] definitions return the supplied address and ignore the size argument.

The cmp_* comparison helpers account for mixed signed/unsigned integral comparisons in their implemented branches. min/max select values, including a variadic reduction; less, greater, and related helpers perform their declared comparisons. trap invokes the compiler trap builtin, while unreachable supplies an unreachable assertion whose reachable execution is invalid.

Raw representation copy into nontrivial objects is not a substitute for their construction or assignment. These helpers impose the selected constructor/assignment/destructor costs, and source-level noexcept constraints must be respected. The separate global allocation operators and smart-pointer owners provide their own lifetime interfaces.

Fresh-storage algorithms

fresh_shallow_copy and fresh_shallow_move copy representations into caller-provided storage and require the appropriate trivial-type/lifetime assumptions and nonoverlap. The shallow move name does not turn byte copying into an overlap-safe move or end the source objects' lifetimes.

fresh_deep_copy placement-constructs destination objects. fresh_deep_move placement-move-constructs each destination and destroys each corresponding source immediately after its move. A partial failed move can therefore leave a source prefix whose lifetimes have ended. This is a destructive relocation interface, distinct from the expression-category move helper. Deep *_assign variants assign existing destination objects instead of placement construction.

fresh_copy, fresh_move, and their assignment forms select shallow or deep machinery according to element traits. Pointer/count operations and contiguous container paths trust their counts; they do not reserve destination storage or change container length. Some iterable deep paths stop at either end, but that behavior does not impose a common capacity clamp on all overloads. Pointer deep-construction helpers provide constructed-prefix cleanup on failure where implemented; iterable loops do not uniformly provide that rollback.

fresh_destroy destroys nontrivial elements and then clears the entire representation range, including trivially destructible elements. fresh_destroy_fast skips clearing and is a no-op for trivially destructible elements. fresh_zero writes zero bytes without first destroying or constructing objects. fresh_set assigns existing elements; fresh_construct placement-copies values into storage. None updates an enclosing container's recorded length.

Work is linear in the processed elements or bytes, except the trivial fast-destroy no-op. Caller-provided storage, source/destination lifetime compatibility, capacity, and failure recovery must match the selected operation. These routines do not supply synchronization.

Null-terminated string operations

The generic string functions operate on integral character types, including wider code units where supported by their declarations. Scalar strlen returns zero for null; bounded length stops at the supplied maximum. Ordinary comparison gives an explicit ordering to null pointers, and a bounded comparison checks that null ordering before its zero-count loop. Do not assume the C library's preconditions or zero-count/null behavior without selecting the actual overload.

strcpy copies through a terminator; strncpy copies up to the bound and pads the remaining requested code units with zeros, without guaranteeing a terminator if the source is at least that long. strcat appends through the terminator; strncat appends at most the requested source units and then writes a terminator. These unbounded destination forms require enough writable space and suitable nonoverlap. Null-input branches generally return the destination or an empty result rather than throwing.

strchr, strrchr, strchrnul, strpbrk, strspn, and strcspn use code-unit searches; character-pointer results can cast away constness. strstr and strnstr use straightforward candidate searches; bounded strnstr bounds the candidate range but its inner comparisons must still be supported by valid source storage. strdup and strndup allocate a new T[], copy, and terminate it; release that result with matching array deletion rather than raw free.

The explicit AVX2 strlen256 and ARM NEON strlen128 routines load entire 32- or 16-byte blocks while looking for zero. They do not guard against a terminator next to an unreadable page boundary; the whole loaded block must be readable. A terminator somewhere in the object is insufficient to justify an out-of-object vector load.

Scalar length, copy, compare, and append are linear in the ranges traversed. Set-membership searches can multiply string and accept/reject-set lengths. The straightforward substring search can require the product of candidate and needle lengths. Duplication adds allocation cost and linear copying.

Bounded string results

sstrlen requires a nonnull source, result pointer, and nonzero maximum, and reports a bound error when no terminator is found. Bounded comparison validates its implemented counts/result pointer and can return at the first differing code unit before proving termination of the remainder. An early match or difference is not a full-range validation pass.

Bounded copy/concatenation forms use explicit source maxima and destination capacities and reject the overlap conditions they test. They can modify a destination prefix before reporting a later capacity error. sstrcpy treats reaching the source maximum as a bounded successful copy and adds a destination terminator when it fits; it does not universally reject an unterminated bounded source. sstrncpy can pad, and copying exactly its count need not append a terminator. sstrncat writes its destination terminator subject to capacity checks, while reaching the supplied source maximum can be accepted.

Bounded character and substring searches have operation-specific termination checks. A first-character search or successful substring can return before scanning the whole haystack; reverse-character search must continue to determine the last match. sstrstr requires the needle's terminator within its maximum. Handle str_error by its enumerator, and preserve valid storage for every range the operation actually reads or writes.

Addresses, pointer checks, and ranges

addressof, addr_of, real_addr, and related address helpers use builtin addressing to avoid an overloaded operator& where implemented. ptr_cast, fn_cast, mem_ptr_cast, reference casts, and the generic cast expose conversions; they do not establish alignment, provenance, correct dynamic type, or object lifetime. as_const returns a const lvalue view and rejects the const-rvalue form; as_mutable removes constness without making an actually const object writable.

addr includes an rvalue form whose result does not extend the temporary's lifetime. not_null currently returns its argument even when null; its null branch is empty. is_alive_ptr tests a pointer wrapper's get() against null, while is_valid_ptr tests its type concept and ignores the runtime value. These names are not validity or liveness proofs.

Runtime byte_ranges_overlap checks integer-address intervals without reading the pointed-to memory, and returns false for null or zero-sized ranges. Its byte-element constant-evaluation branch searches whether either base occurs in the other range rather than ordering unrelated pointers, with linear work in the checked lengths. It does not validate that an interval is mapped or belongs to a live object.

alloca(count, T) multiplies count by sizeof(T) for builtin stack allocation; balloca(bytes, T) and stackalloc(bytes, T) use byte counts. These macros do not construct elements, check multiplication/capacity, or provide an independently releasable lifetime. The storage ends on function return. Fixed cache-line values and estimated stack bounds should not be used as operating-system mapping queries.

Native mapping wrappers

mmap, munmap, mprotect, msync, madvise, mlock/munlock, mlockall/munlockall, mremap, mincore, and the memory-file wrappers forward arguments to native Linux system calls. Sizes are bytes, independent of the pointed-to element type. Pointer-returning wrappers can return encoded negative errors; mmap_failed recognizes the Linux error-pointer range [-4095, -1]. Integer wrappers retain their negative syscall result and do not perform libc-style errno reconciliation.

On width-32 targets, mmap uses mmap2 and shifts the file offset by 12 to obtain 4096-byte offset units. Its wrapper does not reject discarded low offset bits. The supplied address/length/protection/flag requirements and operating-system support remain the caller's responsibility. addrmap/bytemap use read/write anonymous private map_stack mappings for their default tag and return the raw result; another tag has no implementation branch.

brk(nullptr) queries the break. sbrk(increment) returns the previous break after requesting the adjustment, without verifying that it succeeded; callers cannot use that return alone as proof of new writable space. try_unmap skips null and returns one for that branch, rather than the ordinary unmap success value.

Mapping wrappers do not track individual C++ objects and offer no cross-thread ownership scheme. Mapping, protection, remapping, residency, and unmapping costs depend on the operating system and covered pages. Use owning mapping allocators when their more specific cleanup/alignment contracts are needed.

memory/guard.hpp and memory/resource.hpp currently provide no public operational facility. memory/persist.hpp contains an unfinished void persist = delete; declaration rather than a usable persistence API; including it is not a supported persistence mechanism.

micron::memory_block

Defined in header <micron/memory_block.hpp>.

An owning contiguous byte buffer parameterized by a chunk allocator. Its size() and max_size() both report the allocator's current granted byte length.

Storage and special members

Default construction is deleted. Construction with n requests at least n bytes using 64-byte alignment; the returned grant can be larger according to the allocator policy. Every granted byte is part of the exposed range; there is no separate constructed-element count.

Copy construction allocates and copies the complete old grant. Copy assignment reuses equal-length storage or replaces it when grant lengths differ. Move construction and assignment transfer the allocator base and descriptor and clear the source descriptor. Move assignment first releases the destination's old allocation. Destruction returns the grant to the matching allocator.

The constructor taking chunk<byte>&& adopts the descriptor directly. It does not clear the caller's plain chunk, validate provenance, or verify that the allocation used the required allocator/alignment. The caller must perform an actual exclusive ownership transfer.

Complexity and iterator invalidation

Observers and checked access are constant time. Filling and copying are linear in granted bytes. Growth has backend resize cost and can copy the old grant. recreate, a replacing assignment, destruction, and any relocating resize invalidate old pointers, iterators, and references. A descriptor reference continues to refer to the owner's descriptor object, whose contents can change.

Use it for owning byte storage with allocator-selected capacity. It does not supply object construction, typed element alignment beyond the allocation request, or synchronization between readers and writers.

micron::stack_t

Defined in header <micron/memory/stack_constants.hpp>.

A non-owning stack-region descriptor containing addr_t* start and a byte count usize size.

Stack queries

get_stack, get_stack_start, and get_stack_size expose the registered main-stack bounds on a native freestanding build when those bounds are available. Otherwise the native implementation estimates a region below the current frame using default_stack_size and a 4096-byte alignment assumption; it does not query the operating system for the current thread's actual mapping. The wasm branch uses its runtime stack bounds.

These functions do not allocate a stack, extend object lifetimes, prove that a range is readable, or identify every thread's true stack extent. The native estimates are also used by some memory-checking helpers.

micron::str_error

Defined in header <micron/memory/cstring.hpp>.

Status values returned by the bounded sstr* string functions: nullptr_arg, invalid_length, buffer_overflow, ok, and overlap_detected.

Interpretation

The enumerators have consecutive values beginning with zero for nullptr_arg; ok is not the zero value. Test the named enumerator. Success and failure behavior depends on the individual operation's source and destination bounds; a successful bounded copy is not a general proof that every source was null-terminated within its declared maximum.

The bounded operations validate their implemented pointer, count, capacity, and overlap conditions. They do not query the operating system for pointer readability or infer the actual capacity of an allocation.

Example

#include <micron/allocator.hpp>
#include <micron/memory/memory.hpp>

int main()
{
  micron::chunk<byte> memory = micron::allocator_serial<>::create(32);
  micron::memset(memory.ptr, 42, 32);
  bool ok = memory.ptr[0] == 42 && memory.ptr[31] == 42;
  micron::allocator_serial<>::destroy(memory);
  return ok ? 0 : 1;
