Hashing

From micron reference
micron reference › Algorithms

Noncryptographic hashes, incremental XXH64 state, and codec checksums. General hashes live in micron or micron::hashes; checksum functions use explicit initial values and do not share the default-hash dispatch policy.

Complexity, storage, and input ownership

Byte-sequence hashes and checksums perform O(n) work and retain O(1) working state independent of input size. They allocate no dynamic result container and do not modify or retain caller bytes. Fibonacci mixing is O(1). CRC tables occupy static storage; reflected gzip CRC-32 additionally has an 8 KiB slice-by-eight table. Input buffers must be readable for the selected kernel's complete accesses.

Pointer-plus-length APIs take byte counts. Character-pointer convenience overloads scan to the terminating null, excluding that terminator, so embedded nulls truncate the input. Container dispatch uses string_len(container), which chooses len() when available and otherwise size(), and reinterprets cbegin() as bytes. It does not multiply that count by sizeof(value_type): nonbyte containers therefore hash only that many representation bytes. Use an explicit byte pointer and byte length when the entire representation is intended.

Arithmetic hash overloads hash the object's raw representation rather than a normalized mathematical value. Floating +0 and -0, NaN encodings, padding in extended formats, byte order, and target representation can affect results. Hash equality for a key type must be consistent with the equality used by its container; the general API does not establish that property for every type.

Murmur's templated pointer parameter performs tail offsets in T units while block loads treat the address as u64*; use byte-sized T and satisfy the direct word-load alignment/aliasing requirements. Unlike the bounded-load XXH and rapid kernels, this implementation is not a universal unaligned typed-range hash. Low-level Meow residual handling can read a surrounding 16-byte block under a 4096-byte page heuristic and mask unwanted bytes afterward; readable surrounding storage is part of that kernel's access assumptions.

Defaults, seeds, and reproducibility

When zzz selection is enabled by an ARM build or x86 AVX2 and MICRON_NO_ZZZ_HASH is absent, default_hash_128 is zzz128 and default_hash_64 is zzz. Otherwise the defaults are Murmur128 and rapidhash. MICRON_NO_ZZZ_HASH changes default selection; it does not turn every SIMD-specific hash header into a generic backend. The ARM zzz header explicitly requires NEON and little-endian ARM.

default_seed is 0x369bd65914cf0616 and default_seed_32 is 0xf2062906. hash64 has a 64-bit template seed and hash128 a 32-bit template seed. hash<R,seed> uses a 32-bit seed template parameter; when it equals the default 32-bit sentinel, its 64-bit branch delegates to the default 64-bit seed. Explicit named algorithms have their own seed defaults, usually zero, so equal names or input bytes alone do not establish equal results across wrappers.

Runtime seed parameter order is significant: convenience hash64(data,length,seed) differs from rapidhash(data,seed,length), xxhash64_rtseed(data,seed,length), zzz-family runtime forms, and Meow runtime forms. Murmur uses (data,length,seed), while FNV uses (data,seed,length). Template-seeded overloads normally accept (data,length).

hash_types is an enumeration used by compile-time default comparisons, not a runtime algorithm argument. The wrapper dispatches 64-bit results when R is eight bytes, or 128-bit results for its pair-compatible branch. Declaring hash32_t does not add a 32-bit hash<R> branch; unsupported R can instantiate a function with no value result. Fallback paths in hash64/hash128 return zero if no configured case matches. For stored digests or interchange formats, choose an explicit named algorithm, seed, byte encoding, and version rather than the build-selected wrapper.

Vector hash details

The raw z, zz, zzz, and zzzf functions write four u64 words. The x86 legacy kernels use aligned 256-bit output stores, requiring a 32-byte-aligned four-word destination; the width wrappers supply such an array internally. z64, zz64, zzz64, and zzzf64 xor all four words. The 128-bit wrappers pairwise xor words into pair<u64,u64>.

Legacy z/zz/zzz pad the final 32-byte block with zeros and do not mix the actual byte length into final state. Inputs differing only by extra zero bytes within the same final block consequently have identical results. Their empty-input state also cancels the replicated seed during final xor. The zzzf variant adds byte reversal and lane permutations and mixes the seed and length before two final rounds, so it has different digest semantics. The variant names are not interchangeable version tags.

The ARM implementation represents each 256-bit state as two NEON 128-bit halves and implements matching lane shifts/permutations explicitly. The x86 zzz header exposes definitions only under its AVX2 gate; the ARM header rejects unsupported feature/endian configurations. Meow's x86 functions carry target attributes that permit AES/SSE4.1 code generation, but invocation still requires those instructions on the executing processor. No runtime feature detector is supplied.

Checksum updates and compile-time paths

CRC and Adler pointer overloads accept an explicit initial checksum and byte count. Passing a preceding result as the next initial value continues the same recurrence; gzip/iSCSI complement and restore that state internally. Adler normally starts at one. Iterable checksum overloads multiply size() by sizeof(value_type), unlike the general hash container wrapper. Addressable-object overloads hash sizeof(T) representation bytes, including any padding.

CRC lookup tables are generated at constant evaluation. Scalar normal CRC64 and reflected byte recurrences process one byte at a time; gzip CRC32 uses a slice-by-eight scalar kernel. Supported PCLMUL/PMULL builds can select reflected CRC32 folding at 16 bytes and normal CRC64 folding at 64 bytes, while constant evaluation remains scalar. The normal CRC64 polynomial and reflected CRC32 folding constants use different representations and are not interchangeable.

Adler processes blocks of at most 5552 bytes to keep modular-sum intermediates bounded. At runtime, suitable builds use AVX2, SSSE3, or NEON for lengths at least 64; short inputs and constant evaluation use the scalar kernel. CRC/Adler functions are constexpr and noexcept where declared. Unsupported input addresses and lengths are caller errors, with no option/error-code result.

micron::hash_types

Defined in header <micron/hash/hash.hpp>.

Enumeration naming algorithms considered by the convenience hash dispatch.

Enumerators

bernstein32, murmur128, xxhash64, zzz128, zzz, zz, z, zzzf128, zzzf, rapidhash, meowhash128, and meowhash identify families or output-width variants. The default_hash_64/default_hash_128 constants select compile-time branches. Merely having an enumerator does not create an overload accepting it as a runtime selector or ensure that every output-width wrapper implements it.

micron::hashes::xxhash64_stream

Defined in header <micron/hash/xx.hpp>.

Copyable bounded-state incremental XXH64 accumulator with constexpr update and digest operations.

Construction and operations

Construction calls reset(seed), initializing total length, buffered count, and four lane accumulators. update(bytes,n) consumes complete 32-byte stripes and copies fewer than 32 trailing bytes into the internal tail; caller storage can be released after the call. digest() const finalizes a copy of the logical state without consuming or resetting it, allowing more updates afterward. Repeated digest calls with unchanged state return the same value.

Members and complexity

total is the cumulative byte count; seed the selected initial seed; lanes[4] are bulk accumulators; tail[32] stores a partial stripe; buffered is its live byte count. These public fields must retain the invariants established by reset/update. Update is O(n), digest is O(1) because at most 31 tail bytes remain, and storage is constant. stripe is the low-level complete-block operation and does not maintain length/buffer counters on its own. rotate, round, and load are exposed kernels. Copying the state makes an independent checkpoint without retaining input pointers.

micron::hashes::xxhash64_state

Defined in header <micron/hash/xx.hpp>.

Legacy raw XXH64 state record retained alongside the complete xxhash64_stream API.

Fields and limitations

Contains len, four lane words v, four buffered words mem64, memsize, and padding fields. xstate aliases this record. init_seed<seed>() initializes only v; length, buffer size, buffered words, and padding are left uninitialized. No matching public update/digest protocol is implemented for this record. Use xxhash64_stream for incremental hashing rather than treating init_seed as a fully initialized stream.

micron::hashes::__m256_neon

Defined in header <micron/hash/zzz_arm.hpp>.

Implementation aggregate representing a four-lane 256-bit zzz state using two NEON vectors.

Representation

lo stores lanes 0 and 1 and hi stores lanes 2 and 3. Each member is uint64x2_t. Helper operations perform paired NEON loads/stores, shifts, arithmetic, and permutations. It is a register-state carrier without ownership, allocation, or a portable serialized representation.

micron::crc::__simd::__fold_k

Defined in header <micron/hash/crc_simd.hpp>.

Compile-time polynomial constants used to advance a CRC64 state by N bits.

Constants

For polynomial x^64+Poly, static lo is x^N mod Poly and hi is x^(N+64) mod Poly, computed by the consteval helper. The type owns no runtime storage and is specific to the normal-form CRC64 folding kernel; reflected CRC32 uses separate constants.
