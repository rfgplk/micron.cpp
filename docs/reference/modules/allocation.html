Allocation

From micron reference
micron reference › Memory management

Allocation facilities reserve raw byte storage, adapt allocator protocols, and manage bulk storage lifetimes. A byte chunk describes a grant; an owning buffer, resource, container, or caller is responsible for returning it through the matching allocator. Allocating storage and constructing C++ objects are separate operations.

Byte grants and object lifetimes

create/allocate, resize, logical extents, and growth recommendations use bytes. A typed container converts element counts with checked multiplication and converts grants back to element capacity. page_size is the build's configured default page granule; large_page_size is 2 MiB. A byte grant, physical heap block size, mapped page extent, and number of live objects can all differ.

A successful allocation establishes raw storage, not a sequence of constructed nontrivial objects. Use placement construction and explicit destruction as required by the type. Deallocation, arena rewind/reset/release, and descriptor assignment do not implicitly invoke destructors. Every owner must retain enough allocator, alignment, and extent information to release its original allocation correctly.

alloc<T>(bytes) in alloc.hpp casts a byte allocation to T*; it does not interpret its argument as an element count or construct T. free(pointer) releases raw storage through the configured internal backend. The native internal backend can be abcmalloc or the configured C allocation fallback; the wasm target selects wasmalloc. Pair allocation and release from the same configuration and API family.

Checked arithmetic

allocation_checked_add, allocation_checked_multiply, allocation_checked_round_up, and allocation_checked_growth return a success boolean and write the output on success. Checked rounding rejects zero granularity; checked growth rejects a zero denominator or a ratio below one and computes a rounded-up rational growth value. Their throwing wrappers report length errors. allocation_validate_alignment requires a nonzero power of two.

The older to_page and to_granularity helpers perform their own unchecked rounding. In particular, to_granularity<G>(0) produces G, whereas page rounding of zero remains zero. They do not substitute for checked arithmetic at an untrusted size boundary. Memory-operation byte multiplications are generally unchecked and require caller-supplied valid counts.

Native heap implementation

Ordinary native abcmalloc allocations are served by per-thread arenas. Requests up to 512 bytes use the precise TLSF tier; requests from 513 through 4095 bytes use the small TLSF tier. Requests from 4096 through 32768 bytes use the medium buddy tier, through 262144 bytes the large buddy tier, and larger requests the huge buddy tier. The tier names describe heap books, not a promise of operating-system huge pages. Redzone inflation can change routing near a boundary.

TLSF uses first/second-level bitmaps, size-class free lists, splitting, and adjacent free-block coalescing. Buddy books reserve tail metadata, track minimum-block tags, and split/merge power-of-two orders. Per-tier free caches retain recently freed grants before the book's ordinary release path. Cached grants are excluded from is_present even while their book metadata remains allocated.

Backing sheets are normally carved from a reserved inaccessible virtual-address range and committed as read/write mappings. Defaults reserve 256 GiB with 2 MiB carve granules on width-64 targets, or 1 GiB with 64 KiB granules on width-32 targets. These are address-space reservations, not initial physical payload consumption. Released runs return to inaccessible reserved backing and can be reused; failed/exhausted reservation paths can use separately mapped sheets.

Arena construction allocates metadata and the precise tier, and default eager hot-tier configuration also prepares small and medium tiers using a configured fraction of reported system memory. Large and huge tiers are created on demand under the default lazy construction policy. Expansion uses tier-specific curves, a bounded history predictor, retry limits, and per-tier sheet caps. A small requested allocation can therefore trigger substantially larger backing reservations or mappings.

Native alignment, errors, and concurrency

Native block alignment is 32 bytes without redzones and 16 bytes when the ordinary redzone layout is selected. Larger aligned allocations use a stored raw-pointer prefix. Sized/alignment-specific release must match its original convention; ordinary free can recover a valid prefix, whereas plain dealloc expects an allocator block base.

Allocation expansion can return failure to low-level pointer/chunk callers. Integrity failures, configured size constraints, some initialization failures, and double frees can terminate through the native failure policy; allocator adapters can instead report their explicit exception path. These APIs do not all have the C library's uniform null/errno contract. The native global C wrappers are noexcept; an exception escaping one cannot be handled by its caller as a normal C error.

A thread claims a reusable primary arena slot or an overflow arena. A remote free routes through the owning arena's bounded queue and an embedded-node overflow stack. The owner drains pending frees on later heap access or its release path. Completion of the caller's free does not imply that the owner has reclaimed the block. Ring reservation and overflow pushes use retrying atomic operations; the implementation does not provide a general wait-free latency guarantee.

Metadata ownership and structural locks do not synchronize user objects. Native lookup/reporting of another arena is not an atomic snapshot of all its allocations. Coordinate lifetime changes, sheet freezing/relinquishment, and inspection with application activity. Freezing a sheet can make subsequent allocator metadata writes fault. Explicit sheet release also leaves range-index state that must not be interpreted as proof of a currently live mapping. A namespace containing a borrow forward declaration does not supply an implemented public borrowing operation.

Native configuration and diagnostics

ABCMALLOC_CONFIG_HEADER supplies a complete custom profile; otherwise __ABC_AMD64, __ABC_EMBED, or the default amd64 profile is selected. config_enterprise.hpp is a separate profile file and is not selected automatically by the config header. Profile constants control initial metadata/cache sizes, eager tiers, sheet limits, per-tier caches, redzones, guard pages, scrubbing, provenance, retry behavior, and persistence.

MICRON_ABC_STATS enables native heap counters, while MICRON_ALLOCATOR_STATS enables adapter/resource telemetry. Both snapshots expose an enabled field. Optional provenance/poison/redzone checks add work and do not supply full language-level lifetime checking. Byte-count scrubbing is linear in the scrubbed grant.

ABCMALLOC_DOCTOR_HELP adds an off-heap ledger, bounded event history, allocation-site frame-pointer backtraces where configured, reports, leak listings, and fsck/audit. A manual sweep returns anomalies plus repairs and deep-walks only the calling thread's arena; other arenas are counted/skipped to avoid racing their owner. Ledger growth failure degrades tracking to best effort, and retained history can be evicted.

ABCMALLOC_DOCTOR_RESCUE can suppress selected failures by dropping duplicate frees, repairing current-arena metadata, or quarantining/leaking storage. Conservative rescue avoids in-place repair. These actions do not prove that arbitrary corrupted application state is correct. Hardware-fault-assisted guarded reads are implemented only for amd64; its doctor mode installs SIGSEGV/SIGBUS handlers. Exit reports run before DSO teardown, so their live set can contain longer-lived runtime/DSO allocations.

micron::chunk

Defined in header <micron/memory/allocation/kmemory.hpp>.

A non-owning allocation descriptor, aliased to __chunk<T>, containing T* ptr and usize len. It has 16-byte alignment and no destructor that releases storage.

Members and units

The descriptor stores the supplied length without conversion. Allocation interfaces use chunk<byte>, for which len is a byte count. Merely changing T does not multiply or divide the length. to_chunk(ptr, len) reinterprets the pointer as a byte pointer and preserves len unchanged.

Copy and move are memberwise and leave the source descriptor unchanged. Two descriptors can therefore name the same allocation. Ownership transfer requires the surrounding owner or caller to clear the source explicitly.

InterfaceDescription
ptr, lenAddress and reported extent; neither member proves object lifetime or allocator provenance.
operator=(nullptr)Set the pointer to null and the length to zero without releasing storage.
zero()True when either the pointer is null or the length is zero.
invalid()Test the pointer sentinel (byte*)-1.
failed_allocation()Test the distinct internal sentinel consisting of the maximum byte pointer and length 0xFF. This does not recognize every allocation failure representation.

Notes

An uninitialized automatic descriptor has uninitialized members; use value initialization or an explicit {ptr, len} pair. Descriptor operations are constant time. Releasing or resizing the underlying allocation invalidates every descriptor and pointer that still names the old storage.

micron::allocator_traits

Defined in header <micron/memory/allocation/allocator_types/__scheme.hpp>.

A static adapter for allocators that return byte chunks. It accepts the canonical allocate, resize, and deallocate protocol and supported legacy create, grow, and destroy operations.

Allocation and extent

For a compile-time alignment, allocation prefers an alignment-templated allocate, then create, then runtime-aligned allocate or create, then their plain forms. The runtime-alignment overload considers runtime-aligned and plain forms. An alignment template argument is checked at instantiation; a runtime alignment is validated before use.

A result must have a nonnull pointer for a nonzero request, sufficient byte length, and the requested alignment. Custom allocators are checked. A built-in allocator can declare allocator_trusted; its result checks are omitted unless MICRON_ALLOCATOR_CHECKS is defined. Undersized or misaligned results are returned to the allocator before the validation error is reported.

allocation_extent(bytes, alignment) delegates to the allocator's two-argument or one-argument extent function, falling back to the request itself. Containers that reconstruct an allocation from element capacity require a monotonic, idempotent logical extent that can be recovered from that capacity. Returning arbitrary spare physical block space can violate this requirement.

Resizing and release

resize uses an available aligned resize operation. Otherwise it allocates replacement storage, copies the requested preserved prefix bounded by both grants, and releases the old chunk. The compile-time-alignment path can use legacy grow when the request does not shrink and preservation includes the entire old grant; the runtime-alignment fallback does not use that legacy path.

deallocate selects canonical or legacy release operations and ignores null pointers. Pair the same alignment and allocator with allocation and release. has_unsized_deallocate<Alignment> recognizes the tested alignment-templated or plain pointer-only deallocate/destroy forms; a runtime (pointer, alignment) form alone does not satisfy this trait.

recommend delegates to the allocator or uses checked doubling bounded below by the minimum and any available automatic initial size. The maximum usize value reports recommendation overflow.

Complexity and lifetime

Dispatch and validation are constant time. The replacement fallback adds linear work in the copied byte count to backend allocation and release. Traits operate on storage and never construct or destroy user objects. A successful relocating resize invalidates the old grant; a failed replacement allocation leaves its old grant available to the caller, subject to the underlying allocator's own failure contract.

micron::allocator_serial

Defined in header <micron/memory/allocation/allocator_types/serial_allocator.hpp>.

A stateless byte allocator using serial_allocation_policy and the selected abc heap backend. Its default grant policy suits containers that accept page-sized initial slack and factor-three growth.

Allocation policy

For a nonzero request, the default policy grants at least page_size bytes, rounded to a multiple of page_size. A zero request returns an empty chunk. The default alignment is 64 bytes; explicit alignment must be a nonzero power of two.

recommend computes at least the requested minimum and the ceiling of 3 times the current byte count, then applies the policy minimum and granularity. The policy template argument can replace these defaults.

The reported grant is computed from the policy, rather than copied from the physical heap block size. Matching deallocation therefore uses allocator provenance and alignment instead of treating unused physical block space as part of the container's capacity.

Complexity

Policy arithmetic is constant time. Allocation and release have the selected heap backend's costs. An in-place resize does not copy the payload; a relocating resize is linear in the number of preserved bytes, in addition to allocation and release. Geometric recommendations describe a capacity policy; they do not make every backend operation constant time.

The allocator object contains no per-instance pool. Copying or moving an allocator does not copy or move its allocations. Raw storage is uninitialized unless the selected backend or configuration explicitly clears it. share is deleted; the policy's shareable field does not supply shared ownership or synchronization for stored objects.

Arithmetic overflow and invalid alignment are reported through the allocation exception facilities. A nonzero allocation that cannot be satisfied is an allocation failure. Successful resize or grow must replace the caller's old chunk descriptor; a copied descriptor never extends the allocation's lifetime.

The native abc::__abc_allocator<T>::calloc name denotes fetching a chunk; ordinary native fetch is not a zero-fill guarantee. The wasm wrapper uses zalloc, which clears its grant. Native sanitizer builds route the wrapper through the sanitizer's allocation functions.

Notes

Backend calls report allocation failure through the wrapper's exception path. Pointer-only release ignores null, while the native sized wrapper rejects null. A copied wrapper has no ownership of any chunk. Use the policy allocators or allocator_traits when a container requires reconstructible logical grants.

micron::sys_allocator

Defined in header <micron/memory/allocation/abcmalloc/__sys.hpp>.

Effects and constraints

micron::allocator_static

Defined in header <micron/memory/allocation/allocator_types/static_allocator.hpp>.

A bump allocator over an inline static byte array shared by every instance of the same Tag, Bytes, and Alignment specialization.

Storage and allocation

Bytes must be nonzero, and the pool alignment must be a nonzero power of two. Allocation atomically advances the shared cursor after aligning the next address. It grants exactly the requested byte count; padding also consumes the finite pool. A requested alignment greater than the pool alignment is rejected. A zero request returns an empty chunk.

destroy and deallocate do not reclaim individual allocations. resize allocates a new grant and copies the bounded preserved prefix, retaining the old space even when the request shrinks. grow uses a doubling recommendation. used() includes alignment padding.

reset() rewinds the shared cursor. It invalidates every allocation from that specialization and does not invoke object destructors. Call it only after all allocations are no longer in use and without concurrent allocation or reset.

Complexity and synchronization

Allocation uses a compare-exchange retry loop; an uncontended bump performs constant work. Contention can cause retries. A relocating resize is linear in copied bytes. Individual release and reset perform constant work. Atomic cursor reservation does not synchronize subsequent reads and writes to allocated objects.

Use a distinct tag for an independent static pool. Copy and move of allocator objects do not duplicate or transfer pool storage. Exhaustion, size overflow, and invalid alignment are reported as allocation errors.

micron::allocator_monotonic

Defined in header <micron/memory/allocation/allocator_types/monotonic_allocator.hpp>.

A static, tagged monotonic allocator backed by retained upstream blocks. All objects of a specialization use the same block chain and lock.

Storage and lifetime

A block contains its linkage and bump metadata followed by aligned payload. The slow path scans reusable later blocks before allocating another upstream block with at least the configured BlockBytes payload, together with metadata and alignment allowance. Returned grants have exact requested byte lengths.

Individual release is a no-op. The latest allocation can be resized in place when it ends at the current bump cursor, remains aligned, and fits the block. Shrinking that latest allocation can rewind the cursor. Other resizes allocate replacement storage and copy a bounded prefix; the old grant remains consumed.

reset rewinds all retained blocks. release returns owned blocks to the upstream allocator. Both invalidate outstanding allocations and omit user-object destruction. The static pool outlives individual allocator objects; tags separate pools.

Complexity and synchronization

A current-block bump or latest-allocation resize performs constant work under the specialization's TTAS lock. Slow allocation can scan all retained blocks. Copying resize is linear in preserved bytes; reset, release, and aggregate capacity queries are linear in block count. Lock contention adds unbounded waiting.

The lock protects allocator metadata. It does not make overlapping object access safe or permit reset/release while another caller uses an allocation. Use this allocator for a shared phase lifetime that is managed explicitly; use arena_resource for independently owned resource instances.

micron::arena_resource

Defined in header <micron/memory/allocation/allocator_types/arena_resource.hpp>.

An instance-owned monotonic byte resource with optional caller-provided initial storage, marks, and bulk rewind. It is neither copyable nor movable.

Construction and storage

The default resource acquires upstream blocks lazily, using a page-sized configured block request. A block-size constructor changes that request without allocating immediately. An external chunk<byte> or pointer/length constructor borrows the initial span; the default overflow policy is arena_overflow::fail. arena_overflow::upstream permits spill blocks. External storage must remain valid for the resource's lifetime and is never freed by it.

allocate(bytes, alignment) and allocate<Alignment>(bytes) reserve an exact byte grant from a retained block. Runtime alignment defaults to alignof(max_align_t) and must be a nonzero power of two. allocate_objects<T>(count) checks multiplication and reserves aligned raw storage for count objects without constructing them.

resize can extend or shrink the last bump in place; otherwise it reserves replacement storage and copies a bounded prefix. It checks that the old pointer lies in owned storage, rather than proving that the descriptor identifies one exact live allocation. deallocate does not recover bump space.

Marks and bulk lifetime

A successful rewind restores the marked cursor and rewinds later blocks, retaining their storage. It invalidates allocations and marks created after the selected mark. The selected mark can remain reusable.

Marker invalidation retains at most eight serial ranges; exhausting this bookkeeping advances the generation and conservatively invalidates existing markers. reset rewinds every block and invalidates every marker. release frees owned blocks, rewinds external storage, and invalidates every marker. Destruction releases owned blocks. None of these operations invoke destructors for allocated objects.

micron::map_allocator

Defined in header <micron/memory/allocation/allocator_types/map_allocator.hpp>.

A stateless allocator that gives each allocation its own anonymous private native mapping.

Allocation and resizing

The default policy is serial_allocation_policy. Nonzero requests are policy-rounded and then rounded to page_size; the default alignment and automatic initial request are one page. Greater alignments are obtained by overmapping and unmapping the unused prefix and suffix. Returned grants contain the page-rounded capacity.

resize attempts mremap with mremap_maymove for alignments no greater than a page when preservation includes the relevant old prefix. Otherwise it maps replacement storage, copies the bounded preserved bytes, and unmaps the old storage. The returned address can change. destroy unmaps the chunk; it does not run object destructors.

Complexity and notes

Allocation and release make system calls and have operating-system-dependent cost. The replacement path copies a linear number of bytes. mremap can change page-table mappings without an explicit user-space payload copy; this does not imply constant latency.

Use this allocator when allocations require independent page mappings or protection boundaries. Small grants still occupy page-rounded mappings. Alignment/size validation and mapping failures use the allocator exception paths. Every successful relocating resize and every release invalidates pointers into the old mapping.

micron::fixed_map_allocator

Effects and constraints

micron::allocator_huge

Defined in header <micron/memory/allocation/allocator_types/huge_allocator.hpp>.

micron::allocator_guarded

Defined in header <micron/memory/allocation/allocator_types/guarded_allocator.hpp>.

A native mapping allocator with inaccessible guard pages before and after a writable data mapping. The default logical policy is exact_allocation_policy.

Layout and effects

The logical grant is policy-rounded and then rounded to the requested alignment. Its data mapping is page-rounded. The returned address is right-aligned so that ptr + len meets the trailing guard page. Alignment must be a nonzero power of two no greater than page_size; the default is 16 bytes.

Writing the first byte after the reported grant enters the trailing guard page. Writable padding can remain before the returned address within the first data page, so the guard does not place an immediate fault boundary at every byte preceding ptr.

Create/allocate register guarded external provenance. Resize always obtains another guarded mapping, copies the bounded preserved prefix, and destroys the old mapping. Destroy reconstructs and unmaps the entire guard/data/guard range. These operations do not manage object lifetimes.

Complexity and notes

Each allocation incurs whole-page guard overhead and several mapping/protection operations. Resize is linear in preserved bytes in addition to system-call and provenance costs. Returned pointers are invalid after their mapping is destroyed or replaced. Choose it when a trailing allocation-boundary fault is needed; it is not a general bounds-checked object interface.

micron::allocator_immutable

Defined in header <micron/memory/allocation/allocator_types/immutable_allocator.hpp>.

A native allocator for a separately mapped region that can be sealed read-only after initialization.

Effects

Allocation initially creates writable anonymous storage and registers immutable external provenance. Its logical byte grant equals the request; the mapping length is page-rounded. Larger alignments use aligned overmapping. seal(chunk) checks the base, length-derived mapping extent, and immutable provenance, then calls mprotect for read permission only on that mapping.

resize obtains a new writable mapping, copies a bounded preserved prefix, and destroys the previous mapping. It does not automatically seal the new result. Destroy unregisters and unmaps the storage. The default automatic request is one page, and the recommendation uses doubling.

Sealing changes page protection; it does not convert existing C++ pointers into const-qualified pointers or invoke object constructors. Destructors that write object state cannot be run against sealed storage without a separately valid protection/lifetime strategy. Allocation, sealing, and destruction have mapping/protection and provenance costs. Replacement resize adds linear byte copying. Use this allocator for an independent mapping that is populated once and then read; keep its full owning descriptor for release.

micron::allocator_secure

Defined in header <micron/memory/allocation/allocator_types/secure_allocator.hpp>.

A native mapped allocator that requires locked, nondumpable, noninherited storage and explicitly scrubs its grant before release.

Effects and failures

The default policy is serial_allocation_policy; grants are page-rounded and mappings can satisfy greater power-of-two alignments. Creation requires successful mlock, madvise(madv_dontdump), and madvise(madv_dontfork). Failure cleans up the new mapping and reports an allocation error rather than silently accepting weaker properties.

Create/allocate register secure external provenance. Destroy overwrites the grant through volatile byte stores and a compiler barrier, then unlocks and unmaps it. Resize obtains a fresh secure mapping, copies the bounded preserved prefix, and scrubs/releases the old mapping. No in-place resize is used.

Release is linear in granted bytes because it scrubs them, in addition to system-call and provenance costs. Replacement resize copies preserved bytes and scrubs the old grant. Locked-memory limits and operating-system advice support can make allocation fail.

These operations act on this mapping. Copies of secret values made into other storage, registers, or user-defined objects are not tracked. The allocator does not run object destructors or provide concurrent access control.

micron::allocator_temporal

Defined in header <micron/memory/allocation/allocator_types/advanced_abc_allocators.hpp>.

An opt-in interface to native abcmalloc temporal allocations. Results for the same internal size class can alias an already active block.

Effects and constraints

launder obtains an alignment-checked temporal grant, with a default 16-byte alignment. retire routes the matching aligned grant to abcmalloc tombstoning. There is deliberately no ordinary create operation: this interface is unsuitable as a general owning-container allocator.

Temporal blocks are retained in per-class active slots and returned again without an ownership reference count. A later call can therefore overwrite storage named by an earlier result. The caller must coordinate aliasing, object lifetimes, and release. The temporal/tombstone implementation does not establish that each logical request is a distinct live allocation, and retiring one result cannot be interpreted as decrementing a shared-ownership count.

Notes

The active-slot lookup does not revalidate a stored block's tombstone state, and tombstoning does not clear the active slot as ordinary temporal deallocation does. Retirement is therefore not a general reset that guarantees a fresh live temporal allocation on the next call.

Complexity and notes

An active-slot hit performs bounded metadata work within the selected sheet; finding a sheet, expanding the heap, and tombstone reclamation have the native backend's costs. Use only for explicitly controlled scratch reuse where aliasing is acceptable. Repeated acquisition is not a source of independent persistent buffers.

micron::allocator_retiring

Defined in header <micron/memory/allocation/allocator_types/advanced_abc_allocators.hpp>.

A policy allocator whose release tombstones native abcmalloc blocks instead of returning individual blocks to ordinary reuse. The default policy is serial_allocation_policy, with 16-byte default alignment.

Effects and lifetime

Allocation, logical extent, recommendation, and automatic-size operations are inherited from the policy allocator. destroy/deallocate use aligned retirement. Resize always creates replacement storage, copies the bounded preserved prefix, and retires the previous allocation. Sanitizer-owned heaps use ordinary destruction in place of native retirement.

A tombstone prevents that individual block from being granted by the ordinary free list while its sheet survives. A fully drained nonpersistent sheet can still be released and its addresses reused. Allocation and retirement have native backend costs, including possible sheet scans or reclamation. Resize adds linear preserved-byte copying. Use it when delayed block reuse is required within the native allocator's sheet lifetime; account for the storage retained by tombstones.

micron::allocator_persistent

Defined in header <micron/memory/allocation/allocator_types/advanced_abc_allocators.hpp>.

A retiring allocator available only when MICRON_ABC_PERSISTENT is defined consistently for the native backend.

Lifetime contract

Persistent mode tombstones every native size class, disables free-cache regrant, forbids explicit whole-sheet relinquishment, and disables sheet reclamation and self-cleanup. Freed allocations are not returned for a different ordinary allocation, and their sheets remain mapped.

abc::sheet

Defined in header <micron/memory/allocation/abcmalloc/book.hpp>.

A native abcmalloc owner of one backing mapping and its buddy allocation book. tlsf_sheet supplies the corresponding TLSF book for small allocations.

Storage and interface

Construction accepts an arena owner and a byte chunk, optionally reserving a trailing guard-page offset. The mapping is registered in the owner index. Destruction, release, and reset unregister and release the entire backing mapping, invalidating every contained allocation. freeze applies protection to that entire mapping.

Profiles and metrics

The direct vendored configuration selects TINY, KERNEL, or the default SMALL profile unless a complete BBMALLOC_CONFIG_HEADER is supplied. Profiles determine minimum buddy block, TLSF sheet size, small-request limit, region/sheet counts, maximum alignment, and optional order caches. Wasmalloc overrides its own region/alignment limits before including this configuration and prohibits independent static/linker/port pool selection.

capacity, musage, and available report region-book capacity, accounted usage, and remaining aggregate bytes. largest_free reports one obtainable extent after its implemented cache/spare flushing; fragmentation_permille compares it with aggregate available bytes. These are allocator-state metrics, not operating-system resident-memory measurements. get_version packs the vendored major/minor/patch version into an integer.

Complexity and limitations

TLSF searches bounded bitmaps and merges adjacent blocks. Buddy splitting and merging are logarithmic in region/minimum-block ratio. Slow paths can scan regions and acquire or release TLSF sheets. Aggregate availability does not imply a contiguous grant; largest_free can flush retained spare/cache storage and is not a passive metric.

Direct bb metadata and optional statistics are unsynchronized; callers must serialize concurrent use. The wasm namespace wrapper supplies that serialization. No temporal, native tombstone, sheet-freeze, or persistent-address contract is implemented by this backend.

Defined in header <micron/memory/allocation/wasmalloc/allocator.hpp>.

The wasm allocation wrapper used by micron's byte-allocator compatibility layer. The namespace alias abc refers to micron::wasmalloc on that target.

Backend behavior

The wrapper's calloc(bytes) calls zalloc, clears the granted storage, and reports nonzero failure after the underlying allocation operation has released its heap lock. Aligned allocation and release forward to the wasm heap; counts are bytes and no user objects are constructed.

Wasm allocation serializes bbmalloc operations with a heap mutex. On exhaustion it reserves another linear-memory region with separate buddy tags, attaches it, and retries once. The default initial region request is 1 MiB, subsequent region requests grow geometrically, and the wrapper defaults to at most eight regions of at most 256 MiB each, subject to linear-memory limits. It can retry a smaller region when reservation fails, provided the request still fits.

dealloc makes storage reusable inside the heap; it does not shrink WebAssembly linear memory. resize can preserve an address using bbmalloc's in-place rules or allocate/copy/release. The namespace's query_size, within, and is_present acquire the same lock. An ordinary allocation and zalloc differ in whether the granted payload is cleared.

C interface and constraints

The wasm C wrappers return null on failure and set errno to ENOMEM for nonzero failed allocation; invalid alignment sets EINVAL. posix_memalign returns the corresponding positive error and writes the output pointer only on success. pvalloc checks rounding overflow and maps a zero rounded request to one allocation granule.

The wrapper rejects independent bbmalloc pool-selection macros, owns all its linear-memory regions, and does not implement native Linux mapping/protection allocators. The mutex protects heap metadata, not user data. Region growth and payload copying prevent a bounded constant-latency allocation guarantee.
